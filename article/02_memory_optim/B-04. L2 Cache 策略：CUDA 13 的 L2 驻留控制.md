>在 B-01 / B-02 我们讨论了如何让数据“顺畅地抵达”GPU：从合并访问、向量化到异步搬运，目标是把 HBM 带宽喂满。  
>但当你开始优化真实算子（尤其是推理场景），很快会遇到另一个反直觉现象：**HBM 吞吐不高，算力也没打满，性能还是上不去**。  
>很多时候，问题不是“带宽不够”，而是“热点数据没有稳定地待在离计算最近的位置”。在现代 GPU 上，这个位置往往是 **L2 Cache**。

---

## B-04. L2 Cache 策略：CUDA 13 的 L2 驻留控制（兼容 CUDA 12）

L2 Cache 是 GPU 的全片共享缓存。它不像 Shared Memory 那样由你显式读写，也不像寄存器那样只属于一个线程。L2 更像一个“全场公共资源”：所有 SM 都能用，所有 kernel 都会抢。

当你的算子存在明显的热点复用（例如权重块、查找表、KV 元数据、反复迭代访问的中间张量），你真正想要的是：

- **复用的数据尽量留在 L2**（命中更快、DRAM 更少）
- **一次性数据尽量别污染 L2**（避免把热点挤走）

CUDA 从 11 开始提供了“可编程的 L2 驻留控制”（Persisting L2 Cache / Access Policy Window）。**在 CUDA 13 的工程实践里，这套接口仍是主线**：语义稳定、可用性成熟；同时它也能很好地向下兼容 CUDA 12（本文所有代码路径均按 12/13 共同子集设计）。本章按工程索引型方式讲清：**能做什么、怎么做、怎么证伪、哪里会翻车**。

---

## TL;DR（工程结论）

1. **先判断值不值得**：只有当你有“可复用热点”，L2 residency 才可能带来稳定收益；纯 streaming 数据几乎不会变快。
2. **别迷信 hit rate**：判定收益要看三件套：**kernel time ↓ + DRAM bytes ↓ + L2 命中/lookup hit ↑**。
3. **API 不是“锁 L2”**：persisting 的含义是“更倾向保留”，不是 pin；窗口大于 set-aside 时必须考虑 `hitRatio`，否则容易 thrash。
4. **一定要 reset**：实验/业务跑完要清理 policy window 或 reset persisting L2，否则你会得到不可复现的结果。

补充（CUDA 13 语境）：

- **接口不变，但“默认更复杂”**：CUDA 13 常与更新的驱动、更新的架构/缓存规模一起使用，你更容易遇到“并发 kernel/stream 抢 L2”的现实情况；因此 `hitRatio`、reset、以及把窗口控制在“可解释”的范围内，会比旧环境更关键。
- **向下兼容策略**：如果你还要兼容 CUDA 12，不要依赖任何“只在新版本才出现的 profile UI/命名”，指标用 NCU 的同类项对齐即可（本文按语义解释，不绑死单一 metric 名称）。

适用边界（建议先判断再上 residency）：

- **明显 compute-bound 的 kernel**：即使 L2 hit 提升，整体时间也可能几乎不变。
- **大范围随机访问且复用很弱**：热点不稳定，policy window 往往难以给出稳定收益。
- **强并发多 stream/多 kernel 抢同一片 L2**：set-aside 是共享资源，收益可能被竞争稀释。

## 1. 为什么 L2 在现代 GPU 上变得关键

### 1.1 一张线框图：L2 在哪里

```
HBM/DRAM (最慢，容量最大)
   ▲
   │  (dram transactions)
   │
L2 Cache（全片共享，跨 SM）
   ▲
   │  (per-SM access)
   │
SM 0..N：寄存器 / Shared(L1) / Warp Scheduler / Tensor Core
```

Shared/寄存器属于“片上近身武器”，但它们的容量太小，且复用范围有限（thread/block 级）。L2 的特点是：

- **复用范围大**：跨 SM、跨 block，甚至跨 kernel（取决于时序与竞争）
- **行为不可控（默认）**：LRU 类策略 + 各种竞争，热点不一定能留下

因此，当你能**让热点更稳定地留在 L2**，你往往能同时得到两件事：

- DRAM 压力下降（更少 dram bytes / 更少 dram throughput）
- 访问延迟下降（更少长延迟等待）

## 2. CUDA 的 L2 驻留控制：你能“编程”的是什么

CUDA 的模型分两层：**先预留，再定义窗口**。

### 2.1 Set-aside：先从 L2 里划一块“更愿意留给热点”的区域

核心 API：

- `cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size)`

要点：

- `size` 不是随便设：上限由 `cudaDeviceProp::persistingL2CacheMaxSize` 限制
- 这块区域是**全局共享**的：多个 stream/kernel 都会竞争

### 2.2 Access Policy Window：告诉 GPU “这段内存更像热点”

核心 API：

- `cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, …)`

Window 的关键字段（概念层面）：

- `base_ptr`：窗口起点
- `num_bytes`：窗口大小（上限是 `cudaDeviceProp::accessPolicyMaxWindowSize`）
- `hitProp`：命中时更倾向 `Persisting`
- `missProp`：未命中时更倾向 `Streaming`（减少污染）
- `hitRatio`：一个非常重要的 hint（0.0–1.0），用来描述“窗口里有多少比例值得持久化”

### 2.2.1 一张线框图：set-aside、window、hitRatio 的关系

```
            L2 Cache（全片共享）
┌──────────────────────────────────┐
│  normal region (默认缓存行为)     │
│  ┌──────── set-aside ────────┐   │  ← cudaLimitPersistingL2CacheSize
│  │  persisting-preferred      │   │
│  └───────────────────────────┘   │
└──────────────────────────────────┘

Access Policy Window（按 stream 生效）
base_ptr ───────────────► [ window bytes ]
                         ├── hitProp  : 命中时倾向 Persisting
                         ├── missProp : 未命中时倾向 Streaming
                         └── hitRatio : “窗口内有多少比例值得持久化”的提示
```

### 2.2.2 三种典型配置：为什么会“稳”和“抖”

把它想成：你在 L2 里划了一块“更愿意留给热点”的区域（set-aside），但你实际告诉硬件的热点范围（window）可能更大；`hitRatio` 就是在说“窗口里到底有多少是真的热点”。

```
Case A：window ≤ set-aside（最稳，优先推荐）

L2 set-aside:  [████████████████]   (够放下 window 的热点)
window:        [██████████]         (热点基本都能留住)
hitRatio:      1.0（通常也安全）
结果：L2 hit ↑，DRAM bytes ↓，time 更稳定

Case B：window > set-aside，但 hitRatio 合理（可控）

L2 set-aside:  [████████]           (只够留一部分)
window:        [██████████████████] (窗口很大)
hitRatio:      ≈ set-aside / window（只承诺“其中一部分是热点”）
结果：热点子集更稳，非热点倾向 streaming，整体不容易抖

Case C：window >> set-aside + hitRatio=1.0（经典 thrashing）

L2 set-aside:  [████]               (很小)
window:        [██████████████████] (很大)
hitRatio:      1.0（过度乐观，等价于“都想留”）
结果：持续替换/抖动 → L2 hit 下降，DRAM bytes 上升，time 可能“不升反降”
```

### 2.3 为什么 `hitRatio` 是避免翻车的关键

当 `num_bytes` 明显大于 set-aside 大小时，如果你把 `hitRatio` 仍设成 1.0，本质上是在说：

> “这整个窗口我都想长期留在 L2 里。”

现实是：留不下，于是就会出现持续的替换与抖动（thrashing），结果可能**更慢**。

一个实用的工程经验是：

- 如果 `window_size > set_aside_size`，可以尝试  
  \(hitRatio \approx \frac{set\_aside\_size}{window\_size}\)  
  让硬件“只把其中一部分当作热点”。

### 2.3.1 Thrashing 的时间轴（为什么会“不升反降”）

下面这张图刻意把“缓存抖动”画成时间序列：当你试图让一个远大于 set-aside 的窗口都变成 persisting，硬件只能不断把旧的热点踢掉，下一轮又得从 DRAM 重新取回来。

```
时间 t0         t1         t2         t3         t4

访问窗口:   A B C D E F G H I J K L ...（window 很大）
set-aside:  只能容纳 2 份“热点块”

L2(set-aside) 内容演化：
t0: [A B]   命中 A/B
t1: [C D]   A/B 被挤走（替换），访问 C/D
t2: [A B]   又回到 A/B，但它们刚被挤走 → miss → DRAM 取回
t3: [E F]   再替换
t4: [A B]   继续 miss/替换循环……

宏观现象：
- L2 hit rate 看起来“有一点”，但不稳定，且容易下降
- DRAM bytes 反而上升（反复搬同一批数据）
- time 可能更差（替换 + miss 的叠加）
```

### 2.4 Reset：不清理就不可复现

你至少要做其一：

- `cudaCtxResetPersistingL2Cache()`
- 或者把 policy window 关闭（把 `num_bytes` 置 0 或改成 normal 再 set）

不 reset 的后果很真实：你下一次实验可能因为“缓存里已经有热点”而看起来更快，导致结论漂移。

### 2.5 最小可用代码片段（CUDA 13 主线，兼容 CUDA 12）

下面这段代码覆盖你真正会用到的 80%：查询上限 → 设 set-aside → 给某个 stream 设 window → 跑完 reset。

```cpp
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

#define CUDA_CHECK(call)                                                     \
  do {                                                                       \
    cudaError_t _e = (call);                                                 \
    if (_e != cudaSuccess) {                                                 \
      fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__,         \
              cudaGetErrorString(_e));                                       \
      abort();                                                               \
    }                                                                        \
  } while (0)

static void set_persisting_l2(size_t bytes) {
  cudaDeviceProp prop{};
  CUDA_CHECK(cudaGetDeviceProperties(&prop, 0));

  // 允许的最大 set-aside 大小（不同架构不同）
  const size_t max_bytes = prop.persistingL2CacheMaxSize;
  bytes = (bytes > max_bytes) ? max_bytes : bytes;

  // 从 L2 中预留一块 “persisting-preferred” 区域
  CUDA_CHECK(cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, bytes));
}

static void set_access_policy_window(cudaStream_t stream,
                                     const void* base_ptr,
                                     size_t num_bytes,
                                     float hit_ratio /* 0..1 */) {
  cudaAccessPolicyWindow w{};
  w.base_ptr  = const_cast<void*>(base_ptr);
  w.num_bytes = num_bytes;
  w.hitRatio  = hit_ratio;
  w.hitProp   = cudaAccessPropertyPersisting;
  w.missProp  = cudaAccessPropertyStreaming;

  cudaStreamAttrValue attr{};
  attr.accessPolicyWindow = w;
  CUDA_CHECK(cudaStreamSetAttribute(
      stream, cudaStreamAttributeAccessPolicyWindow, &attr));
}

static void reset_persisting_l2() {
  // 让“之前的 persisting 倾向”尽快失效，保证实验可复现
  CUDA_CHECK(cudaCtxResetPersistingL2Cache());
}
```

## 3. 指标与证据链（推荐 Nsight Compute）

### 3.1 最小证据三件套

1. **Time（时间语义）**：kernel time（event 或 NCU 的同类时间指标，例如 `gpu__time_duration`）
2. **DRAM bytes（流量语义）**：总读写字节（例如 `dram__bytes_read.sum`、`dram__bytes_write.sum`）
3. **L2 hit / lookup（缓存语义）**：L2 命中或命中率（例如 `lts__t_sectors_hit_rate.pct`）

### 3.2 常用辅助指标（用于解释“为什么没变快”）

- `dram__throughput.avg.pct_of_peak_sustained_elapsed`（DRAM 是否已接近上限）
- `lts__t_sectors_*` / `lts__t_requests_*`（请求与 sector 的关系能帮助你理解访问效率）

> 指标名会随 NCU 版本与架构略有差异，最稳的做法是：用 NCU 的 memory table sections 先看“同类指标”，再锁定具体 metric 名称。

### 3.3 一条可直接复制的 NCU 命令（指标以“语义集合”为准）

把指标拆成“必须”和“可选”，能显著降低读者上手成本。

```bash
ncu --set full \
  --metrics gpu__time_duration.sum,dram__bytes_read.sum,dram__bytes_write.sum,lts__t_sectors_hit_rate.pct \
  --target-processes all \
  ./bin/your_binary
```

如果你的 NCU 版本不支持其中某个 metric 名称，做法是：打开 NCU GUI 的 Memory Workload Analysis/Cache 相关 section，从同类项里选等价指标即可（结论不依赖“具体名字”，依赖的是 **time/DRAM/L2** 这三个语义维度）。

## 4. 实战：三组最小可复现实验（Streaming → Reuse → Residency）

这一节的目标不是“秀 API”，而是让你把实验跑成一个结论闭环。

### 4.1 实验 A：Streaming Baseline（一次性数据）

- **设计**：扫过远大于 L2 的数组一次
- **预期**：
  - L2 hit 不高
  - DRAM bytes 高
  - Residency control 基本帮不上忙（因为没有复用）

### 4.2 实验 B：Hot Reuse Baseline（复用但不做 policy）

- **设计**：反复访问同一段数据（重复多次）
- **预期**：
  - L2 hit 上升、DRAM bytes 下降（但稳定性取决于竞争与替换）
  - 时间可能变好，但不一定稳定

### 4.3 实验 C：开启 Residency（set-aside + policy window）

把实验 B 的热点区域设置为 window。

你会看到两类常见结果：

- **窗口 ≤ set-aside**：更稳的 L2 命中、更低的 DRAM bytes、更一致的 time
- **窗口 > set-aside**：需要 `hitRatio` 管控，否则可能 thrash，出现“不升反降”

### 4.4 工程化 SOP（把实验跑成“可引用”的结论）

1. **热身与隔离**：每个变体先 warmup 1–3 次；尽量避免后台大负载（否则 L2 竞争让结果飘）。
2. **每组实验结束都 reset**：对比 A/B/C 时，组与组之间调用 `cudaCtxResetPersistingL2Cache()`。
3. **先扫窗口与 set-aside**：固定数据规模时，先做一个二维扫：`set_aside_size` × `hitRatio`，找到“收益区间”，再收敛到 2–3 个可解释配置。
4. **证据输出要能贴论坛**：每次打印三件套：`time_ms / dram_bytes / l2_hit_rate`，并把输入规模写清楚（window bytes、set-aside bytes、hitRatio、iters）。

### 4.5 结果记录模板（最小可贴版）

建议至少保留下面这种 3 行对比，方便复现实验与二次讨论：

```text
[A] streaming_baseline: time_ms=2.31, dram_bytes=1.82e9, l2_hit_rate=18.4%
[B] hot_reuse_baseline: time_ms=1.74, dram_bytes=1.05e9, l2_hit_rate=46.9%
[C] residency_on      : time_ms=1.52, dram_bytes=7.90e8, l2_hit_rate=63.2% (set_aside=16MB, window=12MB, hitRatio=1.0)
```

如果 C 的时间没有继续下降，优先检查：`window > set-aside`、`hitRatio` 是否过高、是否存在并发 stream 的 L2 竞争。

## 5. 误区清单（论坛里最常见的翻车点）

1. **把 persisting 当“锁死 L2”**：错，它是倾向策略，不是 pin。
2. **窗口太大 + hitRatio=1.0**：最容易 thrash。
3. **忘记 reset**：导致后续实验结果漂移。
4. **并发 streams 互相打架**：set-aside 是共享的，多路热点会互相挤。
5. **只盯 hit rate 不看 DRAM bytes**：hit rate 上去但 time 不变很常见，原因可能是 kernel 不是 memory-bound，或者瓶颈转移到了别处。
