>在 Blackwell 架构问世的今天，GB200 单卡的显存带宽已经突破了惊人的 **8 TB/s**（HBM3e）。面对这样一个天文数字，很多开发者——甚至是经验丰富的工程师——容易产生一种危险的错觉：认为显存带宽已经不再是瓶颈，代码里随便怎么写，显存都能扛得住。
然而，事实恰恰相反。随着 GPU 算力以更夸张的速度增长（Blackwell 的 FP4 算力甚至达到了 20 PFLOPS），**算访比（Compute-to-Memory Ratio）** 实际上是在急剧恶化的。对于大模型推理（尤其是 Decoding 阶段）和许多科学计算任务来说，Global Memory 依然是那个卡住整个系统脖子的绝对瓶颈。如果你无法高效地从显存搬运数据，那么那些昂贵的 Tensor Core 就只能处于空转状态，看着显存控制器发呆。
本章我们将深入 GPU 的访存子系统。我们不会止步于教科书上简单的“合并访问”定义，而是要从**物理层（HBM 的 Burst 机制）**、**指令层（向量化与发射带宽）**以及**架构层（TMA 与 L2 驻留）**三个维度，重构你对“读取显存”这件事的认知。

## 1. 物理层真相：HBM3e 的“最低消费”与合并访问的本质

要优化显存，我们首先得理解显存颗粒（DRAM Device）的脾气。当我们写下一行 C++ 代码 `float val = data[i];` 时，我们往往认为自己在请求 4 个字节的数据。但在显存颗粒（DRAM Device）看来，并不存在“4 字节”这种读取操作。

### HBM 的原子粒度：Sector
现代 GDDR 或 HBM 显存有一个物理上的原子操作粒度，称为 **Sector**，大小通常为 **32 字节**。这意味着，无论你的程序逻辑请求的数据多么微小——哪怕只是读取一个 `char`（1字节）——显存控制器都必须向总线发送指令，搬运完整的 32 字节数据。

这意味着，哪怕你的程序逻辑只需要读取 4 个字节的数据，显存控制器发出的请求依然会从 HBM 中搬运 32 个字节回来。更进一步，当这些数据进入 L2 Cache 时，管理粒度会变得更大，通常是 128 字节（Cache Line）
这就像去超市买东西，有些商品是不拆卖的。你想要一颗鸡蛋，超市只能卖给你一整排。

这就引出了 GPU 编程中最古老、但也最重要的一条铁律：**合并访问 (Memory Coalescing)**。这个概念在十年前就存在，但在 HBM3e 时代，它的物理含义变得更加严苛。

### 重新理解“合并访问 (Coalescing)”
试想一下，如果一个 Warp 中的 32 个线程，正在尝试读取显存中的数据，但它们的访问模式是**跨步（Strided）**的——比如线程 0 读取地址 `0`，线程 1 读取地址 `32`，以此类推。GPU 的 Load/Store Unit (LSU) 会像交警一样，检查这 32 个请求的地址分布情况：

在这种情况下，虽然每个线程只想要 4 个字节，但它们请求的地址彼此间隔太远，无法落在同一个 Sector 内。GPU 的 **Load/Store Unit (LSU)** 被迫将其拆分为 32 个独立的内存事务。显存总线不得不忙碌地搬运 $32 \times 32 = 1024$ 字节的数据。

完美场景：如果这 32 个线程访问的是一段连续的内存地址（例如 data[0] 到 data[31]），这 128 字节的数据刚好能填满 4 个 32 字节的 Sector，或者 1 个 128 字节的 Cache Line。此时，LSU 只需要向显存发起极少量的事务请求，总线利用率是 100%。

灾难场景：如果访问是跨步的（Strided）或者随机的，比如线程 0 访问地址 0，线程 1 访问地址 32，以此类推。虽然每个线程只想要 4 个字节，但因为它们落在不同的 Sector 上，显存控制器被迫发起了 32 次独立的 32 字节传输。总共搬运了 1024 字节，但真正有用的只有 128 字节。在这 1024 字节中，真正被计算单元需要的只有 $32 \times 4 = 128$ 字节。**有效带宽利用率仅为 12.5%。** 剩下的 87.5% 的带宽资源，全部被无用的“废廷”数据占用了。在 8 TB/s 的带宽下，你实际只能用到 1 TB/s，这种浪费是任何算法优化都无法弥补的。

因此，所谓的“合并访问”，本质上就是**让 Warp 内 32 个线程的请求，尽可能落在最少数量的 32-byte Sector（或 128-byte Cache Line）中**。这是所有优化的基石，做不到这一点，后续的 TMA、L2 优化都无从谈起。

## 2. 指令层进阶：从“搬砖”到“托盘”

假设你已经完美做到了地址对齐，带宽利用率就能达到 100% 吗？未必。随着 GPU 显存带宽越来越大，瓶颈可能会发生转移——从显存带宽转移到 **指令发射端 (Instruction Issue)**。

### 2.1 标量指令的发射瓶颈

带宽（路宽）够大没用，还得看你的发令员（Warp Scheduler）能不能忙得过来。让我们剥开 GPU 的皮，看看 **Warp Scheduler（Warp 调度器）** 到底在干什么，你就明白为什么向量化能解决瓶颈了。

#### 形象的比喻：发令员与搬砖工

想象一个场景：
*   **HBM (显存)**：是一个堆满砖头的仓库。
*   **LSU (Load/Store Unit)**：是负责搬砖的卡车队。
*   **Warp Scheduler (调度器)**：是**发令员**。他手里拿着大喇叭，每一秒钟只能喊一声命令。

**场景 A：标量指令 (`float`) —— 累死发令员**
你要搬 **4 块砖**。
*   **代码**：`val1 = data[0]; val2 = data[1]; val3 = data[2]; val4 = data[3];`
*   **发令员的工作**：
    1.  喊第一声：“去搬第 1 块砖！”（发射 `LDG.E.32`）
    2.  喊第二声：“去搬第 2 块砖！”（发射 `LDG.E.32`）
    3.  喊第三声：“去搬第 3 块砖！”（发射 `LDG.E.32`）
    4.  喊第四声：“去搬第 4 块砖！”（发射 `LDG.E.32`）
*   **结果**：发令员喊了 **4 次**。如果发令员每秒只能喊 1 次，这就耗费了 4 秒。哪怕卡车跑得飞快，也被发令员的语速卡住了。

**场景 B：向量化指令 (`float4`) —— 解放发令员**
你还是要搬 **4 块砖**。
*   **代码**：`vec_val = ((float4*)data)[0];`
*   **发令员的工作**：
    1.  喊第一声：“去把这 **4 块砖打包** 一起搬回来！”（发射 `LDG.E.128`）
*   **结果**：发令员只喊了 **1 次**。耗时 1 秒。

**结论**：在场景 B 中，发令员省下的那 3 秒钟，可以用来喊别的命令（比如“去算个加法”、“去算个乘法”）。这就是**解决发射瓶颈**。

### 2.2 硬件层面的物理真相

回到 GPU 微架构，SM 内部的 **Warp Scheduler** 决定了这一切。

#### 物理限制：Issue Slots (发射槽)
每个 Warp Scheduler 在每个时钟周期（Clock Cycle）内，能发射的指令数量是**极其有限的**（通常是 1 条，双发射架构下可能是 1 条计算 + 1 条访存）。这是一个硬指标：**Instruction Issue Rate (指令发射率)**。

#### 算笔账：为什么要省指令？
假设你需要读取 128 字节的数据（Warp 中每个线程读 4 字节）：

1.  **用 `float` (32-bit)**：
    *   你需要写 4 条指令。
    *   **后果**：Warp Scheduler 必须连续占用 4 个周期来把这些“搬运命令”发出去。在这 4 个周期里，Scheduler **没空发射数学计算指令**。流水线被塞满了“搬运请求”。
    *   这叫 **Instruction Bound（指令发射受限）**。

2.  **用 `float4` (128-bit)**：
    *   一条 `LDG.E.128` 指令，携带的信息量是 `float` 的 4 倍。
    *   **后果**：Warp Scheduler 只需要 **1 个周期** 就能把“搬运 128 位数据”这个任务下发给 LSU（Load/Store Unit）。剩下的 3 个周期，Scheduler **空闲**出来了！它可以去发射 `FFMA`（乘加运算）指令。
    *   这叫 **Latency Hiding（延迟掩盖）**。

**SASS 汇编视角**：
*   **标量版**：`LDG.E R0, [R2]; LDG.E R1, [R2+4]; ...`（消耗 4 个发射周期）
*   **向量版**：`LDG.E.128 R0, [R2];`（消耗 1 个发射周期）

### 2.3 编译器魔法：指令是怎么拼起来的？

这就触及到了编译器原理。我们需要区分 **编译时（Compile Time）** 和 **运行时（Runtime）**。

#### 1. 怎么拼的？（编译器的静态打包）
当你写下代码时，`nvcc` 编译器会像一个“俄罗斯方块高手”一样审视你的代码。它寻找的是**连续性**。

*   **情况 A：显式向量化（推荐）**
    *   代码：`float4 val = ((float4*)ptr)[idx];`
    *   行为：编译器直接生成 `LDG.E.128`。这是最稳妥的。
*   **情况 B：自动向量化**
    *   代码：写了 4 行连续的 `val0 = ptr[i]; val1 = ptr[i+1]; ...`
    *   行为：编译器在优化阶段（PTXAS）发现这 4 个变量地址连续且无依赖，于是把它们**“吃”**进去，**“吐”**出一条宽指令 `LDG.E.128`。

#### 2. 不够拼怎么办？（余数处理）
如果你的数据量不是 4 的倍数（例如只有 3 个 float），编译器会“看菜下饭”，绝不等待。

*   **场景 1：只有 1 个 float**
    *   编译器生成 1 条 `LDG.E.32`。效率低，但能跑。
*   **场景 2：有 3 个 float (float3)**
    *   并没有 `LDG.96` 这种指令。编译器会拆解成：1 条 `LDG.E.64`（搬前两个） + 1 条 `LDG.E.32`（搬第三个）。
    *   **后果**：发令员需要喊 **2 次**。
*   **场景 3：强行拼（危险操作）**
    *   只有 3 个有效数据，强行用 `float4` 读。
    *   **后果**：硬件会老实搬运 4 个。如果第 4 个地址越界，程序直接崩溃（Illegal Memory Access）。

#### 3. 核心区别：向量化 vs 合并访问 (Coalescing)
这是两个维度的概念，不要混淆：

| 维度 | **向量化 (Vectorization)** | **合并访问 (Coalescing)** |
| :--- | :--- | :--- |
| **方向** | **纵向** (一个线程，一次拿更多) | **横向** (Warp 内 32 个线程，大家一起拿) |
| **发生时间** | **编译时** (编译器决定指令宽度) | **运行时** (硬件合并请求) |
| **不够拼时** | 编译器拆成多条小指令 | 内存控制器拆成多个小事务 |
| **是否等待** | **否** (看到啥指令就发啥) | **否** (看到几个请求就发几个) |

**总结**：向量化本质上是提高了**“单条指令的信息密度”**。它让调度器用更少的口水（指令数），指挥 LSU 搬运了同样多的砖头（数据量），从而把宝贵的发射带宽留给了真正的数学计算。

## 3. 架构层革命：从 `cp.async` 到 Hopper TMA

做好了对齐，也用了向量化，性能还能提升吗？
能。因为我们依然面临一个架构上的痛点：**数据中转**。

在传统的 GPU 架构中，数据从 Global Memory 搬运到 Shared Memory（这是 GEMM 等算子的必经之路），必须经过 **寄存器 (Register File)** 中转。路径是：
`HBM -> L2 -> L1 -> Register -> Shared Memory`

寄存器是 GPU 上最昂贵、最稀缺的资源。用宝贵的寄存器去充当“搬运工”，会导致 Kernel 的 Occupancy（占用率）下降，限制了并发能力。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/a9d82b4d81514a9c85400cefeeeadcbb.png)

### Ampere 的尝试：异步拷贝
为了解决这个问题，NVIDIA 在 Ampere (A100) 架构中引入了 `cp.async` 指令。这是一次重要的尝试，它建立了一条从 L1 Cache 直接到 Shared Memory 的旁路，数据不再经过寄存器。这极大地解放了寄存器资源。但它依然是一条“指令”，需要 CUDA Core 去计算地址、去发射。
### Hopper 的终极形态：TMA
到了 Hopper (H100) 架构，NVIDIA 彻底重构了访存子系统，引入了 **TMA (Tensor Memory Accelerator)**。

TMA 不再仅仅是一条指令，它实际上是 SM 旁边的一个**独立的智能 DMA 引擎**。在 Hopper 架构下，SM 中的 CUDA Core 不再需要亲自去计算地址、判断边界、发射指令。

工作流程发生了质变：
1.  **Host/SM** 创建一个“搬运描述符 (Descriptor)”，里面详细描述了数据的形状（比如 4D Tensor）、步长（Stride）、以及目标 Shared Memory 地址。
2.  **SM** 只需向 TMA 发送一条“启动”指令。
3.  **TMA** 接管一切。它全自动地计算复杂的地址，处理 Tensor 的边界 Padding，并将数据从 HBM 高速搬运到 Shared Memory。
4.  在此期间，**SM 的计算核心完全解放**，可以全速进行数学运算。

更令人震撼的是 **TMA Multicast (多播)** 技术。在大模型推理（如 MQA/GQA）中，多个 Head 可能需要读取同一份 KV Cache。TMA 可以从 HBM 读取一次数据，然后**同时写入多个 SM 的 Shared Memory**。这直接打破了物理带宽的限制，让等效带宽翻倍，是现代 LLM 推理优化的核心技术。

## 4. 缓存层策略：从 L2 驻留到 Blackwell 单体架构

数据搬得再快，也不如“不用搬”。
随着 GPU L2 Cache 容量从 Ampere 的 40MB 激增至 Blackwell 的更大容量，**L2 缓存管理**已成为继 HBM 带宽之后的第二战场。

### 4.1 痛点：传统 LRU 在 AI 负载下的失效
传统的 Cache 管理采用 **LRU（最近最少使用）** 策略进行驱逐。这在通用计算中很有效，但在深度学习（特别是 LLM 推理）中却存在致命缺陷。

数据访问模式呈现极端的两极分化：
*   **权重 (Weights)**：每一层、每一个 Batch 都要反复使用，是绝对的**“热数据”**。
*   **激活 (Activations)**：流式数据，这一层算完就扔，是**“过客”**。

如果任由 LRU 管理，巨大的流式激活值往往会把宝贵的权重数据从 L2 中“挤出去” (**Cache Thrashing**)。结果就是，当计算下一个 Token 时，GPU 又不得不去慢速的 HBM 中重新加载权重，导致带宽浪费和延迟增加。

### 4.2 软件定义：显式 L2 驻留控制 (Access Policy)
CUDA 12 赋予了开发者控制 L2 驱逐策略的权力。通过 `cudaStreamSetAttribute` API，我们可以将 L2 Cache 逻辑上划分为两个区域：

1.  **Persisting (驻留区)**：我们将权重数据标记为“驻留”。这相当于告诉硬件：“这块数据我还要用，哪怕它最近没被访问，也别把它踢走。”
2.  **Streaming (流式区)**：存放临时数据，优先被驱逐。

**代码实战：**
```cpp
// 定义策略：设置 L2 驻留窗口
cudaStreamAttrValue stream_attribute;
stream_attribute.accessPolicyWindow.base_ptr  = d_weights; // 权重指针
stream_attribute.accessPolicyWindow.num_bytes = weight_size;
stream_attribute.accessPolicyWindow.hitRatio  = 1.0;       // 100% 驻留
stream_attribute.accessPolicyWindow.hitProp   = cudaAccessPropertyPersisting; // 命中则驻留
stream_attribute.accessPolicyWindow.missProp  = cudaAccessPropertyStreaming;  // 未命中则流式

// 1. 应用策略
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute);

// 2. 执行计算 Kernel (此时读取权重的行为已被优化)
gemm_kernel<<<grid, block, 0, stream>>>(d_weights, ...);

// 3. 恢复默认 (避免影响后续操作)
stream_attribute.accessPolicyWindow.hitProp = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute);
```

**配合战术：Non-Temporal Reads (`LDG.NT`)**
对于那些只读一次的数据（如 `input + bias` 中的 input），我们应该在 Kernel 中使用 `__ldg_nt()` 函数。这会生成 `LDG.NT` 指令，告诉 L2 Cache：“这条数据我是路过的，不要把我放在 Cache 里占位置”。这变相增大了热数据的可用空间。

### 4.3 硬件演进：CUDA 13 与 Blackwell 的质变
到了 CUDA 13 和 Blackwell 架构时代，虽然 API 接口保持不变，但底层的物理实现和系统级控制发生了翻天覆地的变化。

#### ① 物理层质变：回归 Monolithic L2（单体 L2）
*   **Hopper (H100) 的挑战**：L2 Cache 是 **Split（分裂）** 的，分为两个独立的物理分区。如果 Grid 映射不当（Partition Camping），数据可能只驻留在其中一半 L2 中，导致有效缓存容量减半。
*   **Blackwell (B200) 的回归**：架构回归了 **Monolithic（单体）L2 Cache** 设计。
    *   **统一地址空间**：现在标记为 "Persisting" 的数据可以真正利用完整的 L2 容量。
    *   **无碎片化**：开发者不再需要为了迎合 L2 分区而做复杂的 Block Swizzling，驻留命中率显著提升。

#### ② 系统级隔离：MLOPart
CUDA 13 为 Blackwell 引入了 **MLOPart (Memory Locality Optimization Partition)**，这是一种比 Stream 更宏观的资源隔离。
*   **硬隔离**：你可以创建一个专门的 Partition，拥有独立的 **L2 Cache 配额**。
*   **应用**：在大模型推理中，可以将 KV Cache 锁在一个独立的 MLOPart 中，物理上隔离掉其他任务对 L2 的干扰。

#### ③ 噪音消除：Green Contexts 与 Spilling 优化
*   **Green Contexts**：提供了更细粒度的故障和资源隔离，防止不同 Context 间的数据争抢导致 Cache 颠簸。
*   **Register Spilling to Shared Memory**：这是 CUDA 13 的一大隐形优化。寄存器溢出数据可以选择优先进入 **Shared Memory** 而非 L2。这意味着“溢出垃圾”不再污染 L2 Cache，让 L2 更纯粹地服务于真正的热数据（权重）。

### 4.4 总结：现代缓存管理最佳实践

在 2025 年，榨干 L2 Cache 的标准作业程序（SOP）如下：

1.  **坚持使用 API**：继续使用 `cudaStreamSetAttribute` 标记权重矩阵。在 Blackwell 上，你将自动享受单体 L2 带来的性能红利。
2.  **指令级配合**：对一次性数据严格使用 `LDG.NT`。
3.  **拥抱新特性**：在多租户或超大模型场景下，探索使用 **MLOPart** 进行物理级缓存隔离。
## 5. 总结：构建现代访存思维

回顾本章，我们完成了一次从“微观”到“宏观”的认知升级。我们发现，在 2025 年，优化 Global Memory 不再仅仅是“对齐地址”那么简单，而是一个系统工程：

1.  **基础 (Basics)**：**对齐 (Coalescing)** 是物理定律，必须遵守。这是为了适配 HBM 的 Burst 粒度。
2.  **进阶 (Advanced)**：**向量化 (`float4`)** 是为了突破指令发射瓶颈，提升流水线效率。
3.  **专家 (Expert)**：利用 **TMA** 卸载地址计算和搬运压力，利用 **L2 Persistence** 手动管理缓存生命周期。

在接下来的代码实战中，我们将构建一个 Micro-Benchmark，亲手测试这几种模式在带宽上的巨大差异，让你亲眼见证优化带来的数倍性能提升。
