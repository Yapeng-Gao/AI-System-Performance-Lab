> B-05 的结论是：对时延敏感、多 GPU、严格 SLA 的路径，默认转向显式内存管理。  
> 显式路径的第一道物理门槛不是 `cudaMemcpyAsync` 这个 API 名，而是 **Host 侧缓冲区是否允许 DMA 直达**。  
> 写了 Async、开了多 Stream，却仍然串行——多数时候，问题出在 pageable staging、默认流隐式同步，或 Copy Engine / 主机内存带宽已经饱和。

---

## B-06. Pinned Memory 与 DMA：H2D/D2H 吞吐上限与 Overlap 条件

## TL;DR（工程结论）

1. **Pageable 上的 `cudaMemcpyAsync` 不是真异步**：驱动通常先把数据 stage 到临时 pinned buffer，再交给 DMA。CPU 参与、吞吐更低，也更容易和其他流发生串行化。
2. **Pinned 是 DMA 直达与真 overlap 的物理前提**：`cudaMallocHost` / `cudaHostAlloc` 锁定物理页后，Copy Engine 才能不经 CPU 中介搬运；`cudaHostRegister` 可用，但常见更慢、更吃 NUMA/对齐细节。
3. **Overlap 要三条件同时成立**：pinned + 非默认 stream + 设备支持 concurrent copy/compute（看 `asyncEngineCount`）。经典流水线是「同 stream 内 H2D→Kernel 保序，跨 stream 的不同 chunk 重叠」；H2D∥D2H 还要求足够 CE，以及主机 DRAM/NUMA 带宽跟得上。
4. **吞吐上限是木桶**：`min(PCIe 有效带宽, 主机内存带宽, 驱动/小包启动开销)`。小传输 latency-bound，大传输才逼近链路墙；双向合计常低于“两倍单向”。
5. **Zero-Copy（mapped pinned）省的是 memcpy launch，不省 PCIe**：离散卡上只适合“触达少、几乎不复用”的路径；反复访问等于反复打穿 PCIe。

## 1. 为什么“写了 Async 仍不加速”

A-08 已经演示过：Pinned + 多 Stream 可以把 H2D / Compute / D2H 叠起来。  
B-05 则把读者推到显式 `cudaMemcpyAsync`。  
本章补的是中间那层：**什么时候 Async 是真的，什么时候只是 API 长得像异步**。

典型翻车形态有三类：

```
(1) 伪异步
pageable host ──staging──► temp pinned ──DMA──► device
                 ▲
              CPU memcpy（同步点藏在这里）

(2) 伪 overlap
同一默认流 / 同流依赖：Copy 与 Kernel 在时间轴上首尾相接，看起来“流水”，其实串行

(3) 链路打不满
单向 H2D 还行，双向 H2D∥D2H 合计远低于 2×：
CE 不够，或主机内存/NUMA 先成为瓶颈
```

本章要回答的工程问题只有一句：

> 给定这块主机缓冲区和这条传输路径，你能拿到的 H2D/D2H 吞吐上限是多少？Overlap 的成立条件是否齐全？

---

## 2. 物理模型：Staging、DMA、Copy Engine

### 2.1 Pageable 为什么必须 staging

默认 `malloc` / `new` 拿到的是 **pageable** 内存：OS 可以把它换出到磁盘。  
GPU 的 DMA 引擎需要稳定的物理地址；它不能对“可能不在内存里”的页直接发起总线事务。

因此，对 pageable 的 `cudaMemcpy(Async)`，驱动常见路径是：

1. 在驱动管理的 pinned staging buffer 上准备一块窗口；
2. CPU 把 pageable 数据拷进 staging（可能触发 page fault）；
3. DMA 再把 staging 搬到 device；
4. 大块数据会按窗口反复 stage → DMA。

代价很直接：**多一次主机侧拷贝 + 可能的同步语义**。  
官方 Runtime API 的 sync behavior 也写明：pageable H2D 在启动前可能先做 stream sync，并把“返回”定义在 staging 完成附近，而不是最终 DMA 完成。

### 2.2 Pinned：把物理页钉住，交给 DMA

Pinned（page-locked）内存保证对应物理页常驻 RAM。  
DMA 拿到页帧列表后可以直接读写，CPU 不必再当搬运工。

```
Pinned host  ──────────────── DMA / Copy Engine ────────────────► Device HBM
Pageable     ──CPU memcpy──► staging pinned ──DMA──► Device HBM
```

这就是为什么：

- 同样调用 `cudaMemcpyAsync`，pinned 往往更快；
- 只有 pinned，才谈得上与 kernel 真正 overlap。

### 2.3 Copy Engine 与 `asyncEngineCount`

现代 GPU 上，数据搬运和计算通常由不同硬件引擎完成：

- **Compute Engine**：跑 kernel；
- **Copy Engine（CE）**：走 PCIe / NVLink 的 DMA。

`cudaDeviceProp::asyncEngineCount` 告诉你设备能同时推进几路异步拷贝。  
经验上：

- `>= 1`：才有资格谈 copy∥compute；
- `>= 2`：才更有机会同时推 H2D 与 D2H（具体仍取决于驱动调度与主机侧带宽）。

A-08 讲“怎么叠流水线”；本章讲“叠得起来的硬件配额是什么”。

**Windows / WDDM 额外提醒**：消费级 GPU 在 WDDM 下，驱动可能把 copy 与 compute 调度得更保守，NSYS 上“看起来不重叠”不一定是代码写错。以时间线证据为准，不要只信 API 名字。

## 3. 分配 API 与 flags：该钉什么、怎么钉

### 3.1 三条分配路径

| API | 含义 | 工程建议 |
|---|---|---|
| `cudaMallocHost` | 分配 pinned host 内存 | 最常用的默认路径 |
| `cudaHostAlloc(..., flags)` | 同上，可加 Portable / Mapped / WriteCombined | 需要特殊语义时用 |
| `cudaHostRegister(ptr, ...)` | 把已有 `malloc` 缓冲注册为 pinned | 对接第三方库时有用；吞吐常不如直接 `HostAlloc` |

Pinned 是稀缺资源：钉得太多会挤占 OS 可分页内存，严重时拖垮整机。  
工程默认：**只 pin staging / 热路径 buffer，循环复用，不要在热路径反复 alloc/free**。

### 3.2 常用 flags

- **`cudaHostAllocDefault`**：普通 pinned，加速 `cudaMemcpy*`。
- **`cudaHostAllocPortable`**：对该进程内多个 CUDA context 都视为 pinned（多上下文场景）。
- **`cudaHostAllocMapped`**：映射进设备地址空间，kernel 可直接解引用（Zero-Copy）。
- **`cudaHostAllocWriteCombined`**：写合并缓冲；CPU→GPU 方向有时更快，但 **CPU 读很慢**。适合“CPU 只写、GPU 读”的单向缓冲。

Mapped 并不改变物理距离：数据仍在主机内存，访问仍走 PCIe（或平台等价互联）。

## 4. Overlap 决策表：条件、流水线形态与 NSYS 症状

### 4.1 先澄清一个常见误解

“Copy 和 Kernel 必须在不同 stream”这句话，指的是 **要重叠的那两次操作**，不是“永远不能写在同一条流里”。

经典切块流水线是这样的：

```
Stream 0:  [H2D chunk0][Kernel0][H2D chunk2][Kernel2] ...
Stream 1:           [H2D chunk1][Kernel1][H2D chunk3][Kernel3] ...
时间轴上:   H2D1 与 Kernel0 重叠；H2D2 与 Kernel1 重叠
```

要点：

- **同一 stream 内**：H2D → Kernel 保序（数据依赖正确）；
- **不同 stream 之间**：chunk N 的 Kernel 与 chunk N+1 的 H2D 可以重叠；
- 若把所有 chunk 塞进 **一条** stream，就退化成 `serial`，端到端 ≈ Σ(copy+kernel)。

配套代码用 `--mode serial` vs `--mode overlap` 做公平对照：数据规模、chunk、`kernel-iters` 相同，只改 stream 数。

### 4.2 可执行清单

| 条件 | 不满足时的典型现象 | 怎么证伪 |
|---|---|---|
| Host 缓冲是 pinned | `MemcpyAsync` 仍像同步；吞吐明显低于 pinned 对照 | A/B：`pageable` vs `pinned` |
| 跨 chunk 使用多个非默认 stream | 时间线完全串行，无重叠窗口 | `serial` vs `overlap` + NSYS |
| 设备 `asyncEngineCount >= 1` | 硬件/驱动侧难做 copy∥compute | `cudaGetDeviceProperties` |
| （双向）CE / 主机带宽足够 | H2D∥D2H 合计远低于 2× 单向 | `pinned` 单向 vs `bidir` |
| 没有默认流 / 同步 API 掺局 | 某次同步 `cudaMemcpy` 把全家串起来 | 排查热路径隐式同步 |
| Kernel 足够长 | overlap 与 serial 几乎一样快 | 调大 `--kernel-iters` 再比 |

伪 overlap 最常见的两种写法：

1. **所有工作丢进同一条非默认流**：流内保序，跨 chunk 也无法重叠；
2. 某处使用了 **legacy default stream** 或同步 `cudaMemcpy`，把其他非默认流一并堵住。

判定规则：

```
真 overlap 成立 ⇔
  NSYS 上存在非空时间交集（某 chunk 的 Copy ∩ 另一 chunk 的 Kernel）
  且 overlap 端到端 < serial 端到端（同 mb/chunk/kernel-iters）
  且对照实验只改 stream 拓扑
```

只看“代码里写了 Async”不够。

## 5. 吞吐上限：扫 size、单向、双向

### 5.1 木桶模型

把 Host↔Device 吞吐想成：

\[
BW_{\text{eff}} \approx \min\big(BW_{\text{PCIe有效}},\, BW_{\text{host DRAM/NUMA}},\, BW_{\text{驱动开销等效}}\big)
\]

- **小包**（KB～百 KB）：启动与同步开销占比大，曲线爬坡；
- **中大包**（数 MB～数十 MB）：逐渐逼近链路有效带宽；
- **双向并行**：理论可接近“两路 CE 相加”，但主机内存常常先塌。

PCIe 有效带宽随代数变化很大：Gen3 x16 大约十几 GB/s 量级，Gen4/Gen5 更高。  
**不要拿别人机器的 Gen5 峰值当自己的 KPI**；以本机 `pinned` 单向稳态为上限参考。

### 5.2 本章 MVP 实验矩阵

配套代码 `examples/02_memory_optim/06_pinned_dma.cu` 覆盖：

| 模式 | 配置 | 要回答的问题 |
|---|---|---|
| `pageable` | `malloc` + `cudaMemcpyAsync` H2D | 伪异步的吞吐地板 |
| `pinned` | `cudaMallocHost` + Async H2D | DMA 直达后的单向上限 |
| `serial` | pinned + **1** stream 切块 H2D→Kernel | overlap 的公平串行基线 |
| `overlap` | pinned + **多** stream 切块 H2D→Kernel | 跨 chunk 是否真重叠 |
| `bidir` | pinned + H2D∥D2H | 双向合计是否接近 2× |
| `mapped` | `cudaHostAllocMapped`，kernel 直读 host | Zero-Copy 有效带宽（≠ memcpy） |

输出口径与 B-05 对齐：`first / median / p95`，并给出 GB/s。  
CSV 里带 `bw_note`，避免把 mapped 的“kernel 读 host 有效带宽”误当成 H2D memcpy 带宽。

证据链优先 **CUDA event / wall clock + NSYS 时间线**，不必强上 NCU。

推荐最小跑法：

```bash
./bin/02_memory_optim_06_pinned_dma --mode pageable --mb 256
./bin/02_memory_optim_06_pinned_dma --mode pinned   --mb 256
./bin/02_memory_optim_06_pinned_dma --mode serial   --mb 256 --chunk-mb 16 --kernel-iters 8
./bin/02_memory_optim_06_pinned_dma --mode overlap  --mb 256 --chunk-mb 16 --streams 4 --kernel-iters 8
./bin/02_memory_optim_06_pinned_dma --mode bidir    --mb 256
```

### 5.3 怎么读结果

1. **`pinned` 相对 `pageable` 没有稳定优势（大包）**：先怀疑测法（size 太小、warmup 不足、带宽被抢），再怀疑平台异常。
2. **`overlap` 不比 `serial` 快、NSYS 无交集**：检查是否实际只有 1 条有效流、是否默认流掺局、`kernel-iters` 是否过小；Windows WDDM 下也要保守解读。
3. **`bidir` 合计 ≈ 单向**：更像 CE 数量或主机内存瓶颈，而不是“PCIe 坏了”。
4. **`mapped` 的 GB/s 远低于 `pinned` memcpy**：正常——前者量的是 kernel 经 PCIe 读 host，不是 DMA memcpy 峰值。

## 6. Zero-Copy：什么时候可以省 memcpy

A-07 已经给过禁令：不要把 Zero-Copy 当 Global Memory。  
这里补判定：

**适合**

- 数据很小，或只触达一次；
- 显式 memcpy 的 launch / staging 开销反而更贵；
- 集成 GPU（CPU/GPU 物理同内存）——这类平台 mapped 常常是收益项。

**不适合**

- 离散卡上对同一块 host 缓冲反复读写；
- 需要稳定高带宽喂 Tensor Core / 大 kernel；
- 把 mapped 指针当“自动缓存”用——GPU 侧通常不会按 HBM 语义帮你缓存这块远端内存。

一句话：

> Zero-Copy 消除的是“再拷一份到 HBM”的步骤，不是 PCIe 延迟本身。

## 7. 2024–2026 的工程边界（扩展阅读）

这些内容不要求本章必跑，但写生产代码时值得知道边界在往哪移。

### 7.1 小传输批量化：`cudaMemcpyBatchAsync`

CUDA 12.8+ 引入批拷 API，用来摊销大量小 `MemcpyAsync` 的 CPU/驱动提交开销，并可带 location hint。  
若你的 workload 是“成千上万个不规则小块”，先合并到 pinned staging，或评估 batch API；不要指望单次 4KB Async 打满 PCIe。

### 7.2 Grace / NVLink-C2C 与传统 PCIe+pinned

Grace Hopper / Grace Blackwell 上，NVLink-C2C 提供相干高带宽 CPU–GPU 互联，系统分配内存与 UM 的性能图景和 x86+PCIe 不同。  
ICS’24 等工作表明：在这类平台上，“系统分配 + 硬件相干”可能成为一等公民路径。  
**本章实验仍以离散卡 + PCIe 的 pinned/DMA 模型为主**；有 Grace 机器时，把同一套对照再跑一遍，结论可能翻转——这正是边界，不是矛盾。

### 7.3 多卡 Host↔GPU 带宽

近期系统工作（如 multipath H2D）指出：单卡 PCIe 路径之外，服务器内还可能存在可聚合的中继路径。  
对单进程单卡训练/推理，先把 pinned + overlap 做对；多卡权重唤醒、KV offload 再考虑更激进的拓扑利用。

## 8. 常见误区

1. **以为函数名带 Async 就一定异步**：pageable 会退化；看 sync behavior，不要看名字。
2. **Pinned 无脑全 pin**：挤占系统内存，得不偿失；pin staging，循环复用。
3. **把“同 stream 写 H2D→Kernel”理解成 overlap 失败**：同 stream 保序是正确写法；失败的是“全程只有一条流”。
4. **只报单向峰值，用它外推流水线吞吐**：双向、NUMA remote、小包启动都会让有效吞吐塌方。
5. **`cudaHostRegister` 默认等于 `cudaHostAlloc`**：功能近似，性能与可移植性常更差。
6. **WriteCombined 缓冲被 CPU 反复读**：写路径可能变快，读路径会很难看。
7. **Mapped 当高速缓存 / 用 mapped GB/s 对比 memcpy GB/s**：量纲不同，结论会错。
8. **在 WDDM 上看到不重叠就认定代码错了**：先用 `serial` vs `overlap` 的端到端时间，再看 NSYS。

## 9. 工程 SOP（从症状到处方）

1. **量设备配额**：打印 `name / asyncEngineCount / canMapHostMemory`。
2. **做 A/B**：同 size 下 `pageable` vs `pinned` 单向 H2D；没有稳定差距就先别谈 overlap。
3. **再做 overlap**：先跑 `serial`，再跑 `overlap`（同 `--mb/--chunk-mb/--kernel-iters`）；NSYS 确认跨 chunk 的 Copy∩Kernel，且端到端下降。
4. **压双向**：`bidir`；若合计上不去，查主机内存带宽与 NUMA 亲和。
5. **最后才考虑 mapped**：仅当访问次数少、memcpy 开销主导时保留。
6. **回归**：改动只允许动 host 分配方式 / stream 拓扑；数据规模与 kernel 强度保持不变。

判停建议：

- `pinned / pageable < 1.1`（大包稳态）→ 先查测法与平台，再谈优化故事；
- `overlap` 相对 `serial` 端到端节省 `< 5%` 且 NSYS 无重叠 → 不算 overlap 成功；
- mapped 相对 pinned memcpy 更慢，且访问次数 `> 1` → 默认退回显式拷贝。
