>在 C++ 层面，我们习惯将 CUDA Kernel 看作一个并行的函数调用，通过 `<<<grid, block>>>` 轻松定义成千上万个线程。但在硅片层面，这实际上是一次向 GPU 硬件调度器提交的“工单请求”。
>硬件资源（SM、寄存器、Shared Memory）是有限的，而软件定义的任务（Grid）往往是巨大的。理解这两者之间如何**映射（Mapping）**、**排队（Queuing）**以及**执行（Execution）**，是解决 L2 Cache 抖动、提升 Occupancy 以及消除尾部效应（Tail Effect）的理论基础。

## 1. 逻辑层级与物理层级的“硬着陆”

CUDA 的编程模型不仅是为了方便写代码，更是为了适配 GPU 的硬件层级。如果不理解这种对应关系，优化就无从谈起。

### 1.1 核心映射表 

这是本章最核心的知识点。请务必区分**资源归属（Residency）**与**调度单位**的区别：

| 软件逻辑 (Software) | 硬件调度 (Hardware)               | 资源归属与生命周期                                           |
| :------------------ | :-------------------------------- | :----------------------------------------------------------- |
| **Grid**            | **GigaThread Engine**             | 驻留在 HBM 中。Grid 启动后，由 GigaThread Engine 全局管控 Block 的分发。 |
| **Block**           | **SM (Streaming Multiprocessor)** | **资源预留单位**。Block 一旦被分发到某个 SM，就会占用该 SM 的 Shared Memory 和寄存器，直到所有线程执行完毕才释放。 |
| **Warp**            | **Warp Scheduler / SMSP**         | **指令发射单位**。SM 内的调度器以 Warp (32线程) 为粒度发射指令。 |
| **Thread**          | **CUDA Core (SP)**                | **数据处理单位**。拥有独立的寄存器状态，但在指令流上是被动的。 |

## 2.GigaThread Engine：Grid → Block 的全局调度层
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/a68ee9e8d35f4e97828e542ff7de5a02.png)

### 2.1、GigaThread Engine 是什么

> **GigaThread Engine = GPU 上负责把 Grid 里的 Block，动态分发给各个 SM 的“全局调度中枢”**

**它只负责 Block“去哪里”，不负责 Block“怎么跑”**
它的职责边界非常清晰,只做三件事：

1. **接收 Kernel 启动请求（Grid 维度信息）**
2. **维护全局 Block Pool（尚未执行的 Block)**
3. **在 SM 请求时，派发 Block 给 SM**

---

###  2.2、GTE 在硬件中的位置

```
                   CPU
                 │
          cudaLaunchKernel
                 │
        ┌──────────────────┐
        │   GigaThread     │
        │     Engine       │   ← 全芯片唯一
        └──────────────────┘
                 │
        ┌────────┼─────────┐
        ▼        ▼         ▼
      SM0      SM1       SM2      ... SMN

```

⚠️ 关键认知点
* GTE 不属于任何一个 SM
* 它看到的是 “整个 GPU 的 Block 全局状态”
* 它不知道 Warp、指令、

---

###  2.3、GTE 内部“调度”的对象是什么

#### 2.3.1 Grid 被线性化为 Block 列表

```
Grid:
┌───┬───┬───┬───┬───┬───┬───┬───┐
│B0 │B1 │B2 │B3 │B4 │B5 │B6 │B7 │ ...
└───┴───┴───┴───┴───┴───┴───┴───┘
```

👉对 GTE 来说，Grid ≈ 一个 Block 序列

---

#### 2.3.2 Block 进入“全局 Block 队列”

```
GigaThread Engine:

Block Queue:
[B0][B1][B2][B3][B4][B5][B6][B7]...
```

* 顺序通常是 blockIdx.x/y/z 展开
* ⚠️ **但这是实现细节，不是语义保证**

---

#### 2.3.3 SM 采用 pull model 向 GTE 请求 Block

> **不是 GTE 主动“推” Block
> 而是 SM 空了 → 向 GTE “要” Block**

```
SM2: “我有空位了！”
        │
        ▼
GTE: pop 一个 Block
        │
        ▼
SM2: Block 就位
```

⚠️ 这是 **pull model**，不是 push

---

### 2.4、GTE 视角下的完整时间线（只看“派发”）
⚠️本小节只从 GTE 视角看问题，不讨论 Block 在 SM 内发生了什么。

```
T0: Block Pool = [B0 ... B9]
T1: 派发 B0–B7 → SM
T2: 空闲（没有 SM 请求）
T3: 派发 B8, B9
T4: Block Pool 为空

```
👉 到这里，GTE 的工作已经结束
👉 Kernel 是否结束，GTE 并不知道
### 2.5、GigaThread Engine 不做什么

很多人误会它“很智能”，其实不是。

### ❌ 它不会：

* ❌ 看 Block 的执行时间
* ❌ 预测访存
* ❌ 做负载均衡
* ❌ 感知 Warp / 指令级行为

> GTE 是“分发器”，不是“调度优化器”

---

### 2.6、GTE 与 Occupancy 的关系

GTE 能不能把 Block 派进 SM，**取决于 SM 是否还有资源**：

```
SM 资源：
- Registers
- Shared Memory
- Max blocks
```

如果一个 Block 占用太多资源：

```
SM: [B0]
（没资源了）

GTE: “你虽然还有 block，但我没法给你”
```

👉 **GTE 不能突破 SM 资源上限**

---

### 2.7、一个你必须知道的事实（高阶）

> **GigaThread Engine 在多 Kernel 并发时，也负责跨 Kernel 的 Block 调度**

```
Kernel A: [A0 A1 A2 ...]
Kernel B: [B0 B1 B2 ...]

GTE Block Pool:
[A0 B0 A1 B1 A2 B2 ...]  ← 简化示意
```

⚠️ 具体策略未公开
⚠️ 但 **不是一个 kernel 完了才下一个**

---

### 2.8、一句话记忆模型

> **GigaThread Engine = GPU 的“总调度台”
> SM = 工人
> Block = 工单
> 谁空了，谁去领下一张工单**

## 3. Block 调度：Block → SM 驻留与生命周期管理

Block ID 的线性顺序（0, 1, 2...）并不代表执行顺序，更不代表它们在物理空间上的邻近性。错误的假设会导致严重的性能问题。
>如果说 GTE 解决的是
>“Block 去哪个 SM”
>那 Block 调度解决的是
>“Block 进了 SM 之后会发生什么”
### 3.1、Block 调度在体系中的位置

```
┌──────────────────┐
│  GigaThread      │  ← Block 派发
│   Engine (GTE)   │
└──────────────────┘
           │
           ▼
┌─────────────────────────────────────┐
│        SM（Block 驻留与执行域）       │
│ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │
│ │ SM0  │ │ SM1  │ │ SM2  │ │ SM3  │ │
│ └──────┘ └──────┘ └──────┘ └──────┘ │
└─────────────────────────────────────┘

```

👉 Block 调度发生在 SM 侧，不在 GTE

---

### 3.2、Block 调度的核心规则


1. **Block 是最小调度单位**
2. **SM 有空位才会要 Block**
3. **Block 一旦进 SM，不迁移、不抢占**


---

### 3.3、Block 调度完整流程图

假设：

* 4 个 SM
* 每个 SM 最多同时 2 个 Block
* Grid 有 10 个 Block（B0–B9）

---

#### ⏱ T0：Kernel 刚启动

```
GTE Block Queue:
[B0 B1 B2 B3 B4 B5 B6 B7 B8 B9]

SM0: [   ] [   ]
SM1: [   ] [   ]
SM2: [   ] [   ]
SM3: [   ] [   ]
```

---

#### ⏱ T1：第一次分发（填满 SM）

```
SM0: [B0] [B1]
SM1: [B2] [B3]
SM2: [B4] [B5]
SM3: [B6] [B7]

GTE Queue: [B8 B9]
```

👉 **GTE 不关心“谁快谁慢”，只管填满**

---

#### ⏱ T2：执行中（Block 生命周期开始分化）

```
SM0: [B0] [B1]   ← 都还在跑
SM1: [✓ ] [B3]   ← B2 结束
SM2: [B4] [✓ ]   ← B5 结束
SM3: [B6] [B7]   ← 都慢
```

⚠️ Block 运行时间不一致是**常态**

---

#### ⏱ T3：动态补位（Block 调度的关键瞬间）

```
SM1 → GTE: request block
SM2 → GTE: request block

GTE → SM1: B8
GTE → SM2: B9

结果：
SM0: [B0] [B1]
SM1: [B3] [B8]
SM2: [B4] [B9]
SM3: [B6] [B7]
```

👉 **谁空了谁拿**
👉 **没有“轮询”或“均衡”逻辑**

---

#### ⏱ T4：尾部阶段（tail latency）

```
SM0: [✓ ] [✓ ]
SM1: [✓ ] [✓ ]
SM2: [✓ ] [✓ ]
SM3: [B6] [   ]  ← 最慢的 block
```

🚨 **Kernel 结束时间 = 最慢 Block 的结束时间**

---

### 3.4、Block 调度 = 资源约束调度

```
一个 Block 资源需求：
- 48 KB Shared Memory
- 80 Registers / thread

SM 上限：
- 64 KB Shared Memory
- 65536 Registers
```

结果：

```
SM:
[ Block A ]   ← 占了 48KB
[    X    ]   ← 放不下第二个 Block
```

👉 **不是 GTE 不想调度**
👉 **是 SM 资源拒绝**

---

### 3.5、Block 调度最重要的 4 个“不可变事实”

#### 1️⃣ Block 不会迁移

```
SM1: [B3]  ← 不会中途挪去 SM0
```

---

#### 2️⃣ Block 不会被抢占

```
慢 Block = 慢到跑完为止
```

---

#### 3️⃣ Block 顺序 ≠ 执行顺序

```
blockIdx.x = 0
可能是最后一个结束
```

---

#### 4️⃣ Block 之间没有同步语义

```cpp
__syncthreads(); // 只在 block 内有效
```

---

### 3.6、为什么 Block 调度模型“简单但残酷”

> **GTE + Block 调度
> 是为了“吞吐最大化”，而不是“延迟公平”**

它假设：

* Block 足够多
* Block 工作量相近
* 慢 block 是少数

一旦假设被破坏 → **尾巴效应严重**

---

### 3.7、把 GTE + Block 调度压成一张“脑内图”

```
Block Queue (GTE)
   │
   ▼
[ pop ]
   │
   ▼
SM 有资源？
   │
 ┌─┴─┐
 │是 │──▶ Block 驻留（不可迁移）
 │否 │──▶ 等
 └───┘
```

## 4.位置效应

### 4.1 线性映射的陷阱：Partition Camping
在处理 2D 图像或矩阵时，如果你简单地使用线性 `blockIdx.x` 来映射数据区域，可能会遭遇 **Partition Camping**。
*   **现象**：GPU 的 L2 Cache 是分片（Slice）管理的，每个片对应一段物理内存地址。如果相邻的 Block（往往被调度到不同的 SM 上并发执行）同时访问映射到同一个 L2 Slice 的内存地址，会导致该 Slice 的队列拥塞，而其他 Slice 空闲。
*   **后果**：L2 带宽利用率急剧下降，显存吞吐受限。

### 4.2 解决方案：Block Swizzling (光栅化重排)
为了解决这个问题，高性能算子库（如 CUTLASS、Triton）通常会采用 **Block Swizzling** 策略。
*   **原理**：不按行扫描顺序调度 Block，而是按 Z-Curve（Z 序曲线）或 Tile 顺序调度。这使得并发执行的 Block 在物理内存访问上更加离散，从而均匀利用所有 L2 Slices。
*   **实现**：虽然 CUDA 12 在部分场景下有硬件级优化，但在写 GEMM 或 Conv Kernel 时，手动重映射 Block ID 依然是标准操作。

### 4.3 资源预留与 Occupancy
SM 在接收一个 Block 之前，会检查当前的资源（寄存器、Shared Memory）是否足够。如果不够，Block 就无法启动。
这也是为什么我们说 **Occupancy（占用率）** 是一个物理概念——它描述的是 SM 上实际驻留的 Active Warps 数量。如果你的 Kernel 寄存器用量过大，导致一个 SM 只能塞进去 1 个 Block，那么不仅掩盖不了延迟，甚至可能让 SM 处于“饥饿”状态。
![Block 调度与“位置效应”](https://i-blog.csdnimg.cn/direct/3887bfe5b62d4f17a4725c6d2693bf5f.png)

## 5. Warp：SM 内真正的执行与调度单位
>到目前为止，我们只解释了：
>Block 如何被分发
>Block 如何驻留

但Warp 才是 GPU 上最小的“执行单位”，不是调度给 SM 的单位。
Block 决定“在哪跑”，Warp 决定“什么时候跑”。



---

### 5.1 从 Block 到 Warp 的物理映射

```
一个 Thread Block
┌──────────────────────────────────┐
│ Thread 0  Thread 1  ... Thread 31 │  ← Warp 0
│ Thread 32 Thread 33 ... Thread 63 │  ← Warp 1
│ Thread 64 Thread 65 ... Thread 95 │  ← Warp 2
│ Thread 96 Thread 97 ... Thread127 │  ← Warp 3
└──────────────────────────────────┘
```

关键点：

* **32 个线程 = 1 个 Warp（硬件常量）**
* Warp 是 **编译期就确定的划分**
* 不存在“动态 Warp 组装”


---

### 5.2 Warp 在 SM 中的真实位置

```
                 一个 SM（简化）
┌────────────────────────────────────────┐
│ Register File                           │
│  ├─ Warp 0 registers                   │
│  ├─ Warp 1 registers                   │
│  ├─ Warp 2 registers                   │
│  └─ Warp 3 registers                   │
│                                        │
│ Shared Memory (Block 级共享)           │
│                                        │
│ ┌────────────────────────────────────┐ │
│ │   Warp Scheduler / Issue Unit       │ │
│ └────────────────────────────────────┘ │
└────────────────────────────────────────┘
```

⚠️ 认知重点：

* Warp **不是一个软件概念**
* 每个 Warp 在 SM 内 **有自己的一组寄存器**
* Warp Scheduler 每个 cycle 都在工作

---

## 5.3 Warp 调度器在做什么

> **Warp Scheduler 每个时钟周期选择一个“就绪 Warp”发射一条指令**

```
一个 SM（简化）
┌────────────────────────────────────┐
│ Warp Pool                           │
│  W0  W1  W2  W3  W4  W5  W6  W7     │
│                                    │
│ ┌──────────────────────────────┐   │
│ │   Warp Scheduler              │◄──┘  ← 选 warp
│ └──────────────────────────────┘
│                │
│                ▼
│ ┌──────────────────────────────┐
│ │   Issue Logic                 │  ← 发几条
│ │   (Single / Dual / Multi)     │
│ └──────────────────────────────┘
│      │        │
│      ▼        ▼
│   ALU Pipe   LSU / SFU / Tensor │
└────────────────────────────────────┘
```


Warp Scheduler：选谁
Issue Logic：发几条、发到哪
```
Cycle N:
就绪 Warp 集合: {W0, W2, W5}

Warp Scheduler → 选择 W2
Issue: W2 执行一条指令
```

* “就绪” = 没被 stall（访存、依赖）
* 被选中 Warp 的 **32 个线程锁步执行**

### 5.3.1 Single Issue vs Dual Issue
Single Issue（早期 / 保守模型)
```
Cycle N:
Warp W2 → 发射 1 条指令 → ALU
```

Dual Issue（Volta 以后常见)

```
Cycle N:
Warp W2 →
    ├─ 指令 1 → ALU
    └─ 指令 2 → LSU

```
⚠️ 前提条件非常苛刻：

同一个 Warp

指令类型不同（ALU + MEM）

无数据依赖

👉 不是“两个 Warp 同时跑

### 5.3.2 Multiple Issue
>单 Warp 多 pipeline issue

```
Warp W3
 ├─ FFMA → FP32 Pipe
 ├─ LDG  → LSU
 └─ HMMA → Tensor Core

```

## 5.4 Warp 调度时间线（和 Block 调度明显不同）

```
时间 →
Cycle 0:  Warp 0 执行
Cycle 1:  Warp 1 执行
Cycle 2:  Warp 0 执行
Cycle 3:  Warp 2 执行
Cycle 4:  Warp 1 执行
...
```

👉 **Warp 调度是“指令级、cycle 级”的**
👉 与 Block / GTE 完全不是一个时间尺度

---

## 5.5 分支与 Divergence（Warp 层的核心现象）

```
if (tid < 16)
    A();
else
    B();
```

```
Warp 0:
Threads 0–15  → 执行 A()
Threads 16–31 → 执行 B()
```

执行过程：

```
Phase 1: 执行 A()，后 16 个线程 mask
Phase 2: 执行 B()，前 16 个线程 mask
```
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/555331dee2fa4b9f978cce79b7ac3a4d.png)

⚠️ **不是并行执行**
⚠️ 是 **串行化 + 掩码**

---

## 5.6 Warp 调度如何隐藏延迟（关键性能点）

```
Warp 0: global memory load → stall
Warp 1: ready
Warp 2: ready

Warp Scheduler:
跳过 Warp 0 → 选择 Warp 1
```

👉 **延迟隐藏 ≠ 更快**
👉 是 **“有别的 Warp 可跑”**

这也是 **Occupancy 的真正意义**。

---

## 5.7 Warp 调度的硬约束

* Warp **不会迁移**
* Warp **不会抢占**
* Warp **不能拆分**
* Warp **不跨 SM**

---

## 5.8 Warp vs Block vs GTE 的最终对照图

```
时间尺度 ↓

秒 / 毫秒
┌─────────────────────────────┐
│ GigaThread Engine           │  ← Block 派发
└─────────────────────────────┘

微秒
┌─────────────────────────────┐
│ Block 驻留 / 生命周期        │
└─────────────────────────────┘

纳秒 / cycle
┌─────────────────────────────┐
│ Warp Scheduler              │  ← 指令执行
└─────────────────────────────┘
```

## 6. 尾流效应 (Wave Quantization)

在处理大规模数据时，Kernel 的 Grid Size 设置往往决定了最后的性能“长尾”。

### 6.1 什么是 Wave？
假设你的 GPU（如 A100）有 108 个 SM，每个 SM 资源允许驻留 4 个 Block。那么全卡“满载一波”（Full Wave）能并行处理 $108 \times 4 = 432$ 个 Block。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/429c369d681e456fb36bf8f7556fbddc.png)

### 6.2 整数倍的重要性
*   **完美场景**：Grid Size = 4320。GPU 满载跑 10 波，SM 利用率 100%。
*   **最差场景**：Grid Size = 4321。
    *   前 10 波满载运行。
    *   **第 11 波**：只剩 1 个 Block 需要执行。
    *   **后果**：这 1 个 Block 独占 GPU，其余 107 个 SM 全部空转等待。这就是 **Tail Effect**。

**优化策略**：
1.  **Grid-Stride Loop**：不要让 Grid Size 仅仅等于数据大小。设置一个固定的、足够填满 GPU 的 Grid Size，然后在 Kernel 内部通过循环处理多余的数据。
2.  **Padding**：将任务量补齐到 Wave 的整数倍。

## 7. 索引计算最佳实践

在 GPU 上，整数除法（`/`）和取模（`%`）是极其昂贵的操作（通常需要数十个时钟周期），比浮点乘加还要慢。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/dd8bced976484e31965396b71ecfd7ac.png)

### 7.1 避免动态计算
尽量使用 1D Grid 和 1D Block。如果逻辑上需要多维索引：
*   如果维度是 2 的幂（如 32, 64, 128），编译器会自动将 `/` 和 `%` 优化为位运算（`>>` 和 `&`），这是极快的。
*   如果维度不是 2 的幂，且必须进行坐标变换，考虑在 Host 端预计算好基地址，或者使用 PTX 内联汇编中的优化指令（如 `mad.lo.s32`）。
