## 1. SIMT（Single Instruction, Multiple Threads）理解

### 1.1一句话先定性

> **SIMT = 程序员视角是“独立线程”，
> 硬件执行视角是“Warp 锁步执行”。**

---

### 1.2 SIMT 的“真实物理形态”

#### 1.2.1 程序员看到的世界（逻辑视角）

```
Thread 0: a[0] = b[0] + c[0]
Thread 1: a[1] = b[1] + c[1]
Thread 2: a[2] = b[2] + c[2]
...
Thread 31: a[31] = b[31] + c[31]
```

👉 **看起来是 32 个独立线程**

---

#### 1.2.2 GPU 真正在干的事（硬件视角）

```
            Warp 0
┌─────────────────────────────────┐
│ T0  T1  T2  ...            T31 │
└─────────────────────────────────┘
              │
              ▼
      同一条指令（ADD）
              │
              ▼
┌─────────────────────────────────┐
│ Lane0 Lane1 Lane2 ...     Lane31│
└─────────────────────────────────┘
```

👉 **一条指令，32 个 lane （也叫 SIMD-lane、CUDA-core、ALU-slot）同时执行**
GPU 的 SM 里真正发生的事情是：

 1. 取指、译码、发射单元只拿到 1 条机器指令（比如 FADD）。 
 2. 这条指令被广播到 32 个 lane（也叫SIMD-lane、CUDA-core、ALU-slot）。
 3.  每个 lane把自己的寄存器编号、私有操作数套进去，在同一时钟周期完成计算。 
 4. 结果写回 32 份独立的寄存器文件项。



这就是 **SIMT 的“真相”**。

---

### 1.3 SIMT vs SIMD

#### 1.3.1 SIMD（CPU / 向量机）

```
Vector Register:
[V0 V1 V2 V3]

Instruction:
ADD V = A + B
```

* 程序员显式写向量
* 编译器难度低
* 灵活性差

---

#### 1.3.2 SIMT（GPU）

```
Thread 0 → 标量寄存器
Thread 1 → 标量寄存器
...
Thread 31 → 标量寄存器
```

```
Warp 执行：
ADD r = a + b   （锁步）
```

✅ **像 SIMD**
❌ **但不是 SIMD ISA**

👉 **SIMT = SIMD 的执行方式 + 线程级编程模型**

---

### 1.4 分支下的 SIMT

#### 1.4.1 if 分支示意图

```
if (tid % 2 == 0)
    A
else
    B
```

---

#### 1.4.2 Warp 内发生的真实情况

```
Warp 0:
T0 ✓   T1 ✗   T2 ✓   T3 ✗   ...
```

---

#### 1.4.3 硬件执行顺序（串行化）

```
Step 1:
执行 A
Mask: 101010...

Step 2:
执行 B
Mask: 010101...
```

```
→ Warp 仍是锁步，但被拆成两段
```

⚠️ **这不是线程切换，是“掩码执行”**

---

### 1.5 SIMT 的 Mask 执行机制

👉 **性能损失来自“空转”，不是上下文切换**

### 1.6 SIMT × Memory（为什么 Warp 是访存单位）

#### 1.6.1 Global Memory 合并

```
Warp:
T0 → addr 0
T1 → addr 4
...
T31 → addr 124
```

```
→ 1 次内存事务
```

---

#### 1.6.2 非规则访问

```
Warp:
T0 → addr 0
T1 → addr 1024
...
```

```
→ 多次内存事务
```

👉 **SIMT 决定了访存合并的分析单位是 Warp**

---

### 1.7 SIMT 的“反直觉点”

#### 1.7.1 ❌ 误解 1：SIMT = 真·并行 32 条线程

✅ 实际：

```
1 条指令
32 个 lane
```

---

#### 1.7.2 ❌ 误解 2：分支只是线程问题

✅ 实际：

```

```

---

#### 1.7.3 ❌ 误解 3：多 Warp = 多指令并行

✅ 实际：

```
多 Warp = stall hiding
```

---

### 1.8 SIMT 与 Warp Scheduler 的关系

```
Warp Scheduler：
选择 Warp

SIMT：
规定 Warp 内怎么执行
```

```
Scheduler 选 Warp 0 →
Warp 0 以 SIMT 模式执行 1 条指令
```

👉 **SIMT 是“执行语义”，不是调度策略**

---

### 1.9 一张“终极总结图”

```
Thread (逻辑)
   │
   ▼
Warp (32 threads)
   │   ← SIMT 锁步
   ▼
Instruction
   │
   ▼
32 Lanes (物理执行)
```



> **SIMT 的本质不是“线程并行”，
> 而是“线程级编程 + 向量化执行”。**

## 2. SIMT 的物理本质：One Brain, 32 Hands
在微架构层面，Warp 内的 32 个线程共享同一个 **Program Counter (PC)** 和指令发射逻辑。这意味着它们必须“步调一致”地执行同一条指令。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/a49a96754a3342358cb47848ace67a7a.png)

当一个 Warp 被调度器选中并执行时，硬件层面发生的事情与我们脑海中的“并行”有本质区别。

### 2.1 谓词化执行 (Predicated Execution)
在微架构层面，Warp 共享一个 Program Counter (PC)。这意味着物理上，所有 32 个线程必须在同一时刻指向同一条指令。那么，CUDA 是如何支持每个线程执行不同代码路径的？

答案是 **Predication (谓词化)**。
在 SASS 汇编中，几乎所有的指令都带有一个前缀 `(@P)`。
*   硬件维护一组 **Predicate Registers (P0-P6)**,具体谓词寄存器数量与微架构代际有关，但逻辑模型一致。
*   还有一个物理寄存器 **Active Mask**（32-bit），每一位对应一个线程的激活状态。

当执行指令 `@P0 FADD R1, R2, R3` 时，ALU 并不会智能地跳过某些线程。相反，所有 32 个 ALU 都会通电，但只有那些在 `Active Mask` 中标记为 1 且 `P0` 寄存器为 True 的线程，其计算结果才会被允许**写回**寄存器堆。其余线程虽然也在“空转”，但它们的操作是无效的（NOP）。

### 2.2 逻辑分支的物理代价
当代码遇到 `if (cond) { A } else { B }` 时，硬件执行流程如下：

1.  **评估 (Evaluate)**：所有线程计算 `cond`，更新各自的谓词寄存器。
2.  **分裂 (Diverge)**：硬件检测到谓词不一致。
3.  **分支 A (Serialize)**：Active Mask 被设置为 `Group_A`。执行代码块 A。此时，属于 Group B 的线程对应的 ALU 处于 Idle 状态。
4.  **分支 B (Serialize)**：Active Mask 反转。执行代码块 B。此时，属于 Group A 的线程 Idle。
5.  **重汇聚 (Reconvergence)**：到达编译器标记的汇合点（Immediate Post-Dominator），恢复 Full Mask。

**结论**：在单 Warp、完全交错分支的极端情况下，有效执行效率可下降至 1/32。这就是为什么我们在 Kernel 优化中极其忌讳在 Warp 内部做复杂的控制流判断。

## 3. 独立线程调度 (ITS)：Volta 之后的“罗生门”

NVIDIA 在 Volta 架构（以及随后的 Ampere/Hopper/Blackwell）中引入了 **Independent Thread Scheduling (ITS)**。

> **ITS 不是让 GPU 变成 MIMD**
> **它只是让 Warp 内线程“不会被彼此拖死”**

---

### 3.1没有 ITS 之前：Warp 是“命运共同体”

 🔴 Volta 之前（Pascal / Maxwell）

```
Warp (32 threads)
┌─────────────────────────────┐
│ PC = 0x100                  │
│ Active Mask = 111111...111 │
└─────────────────────────────┘
```

❌ 一个线程卡住，所有线程一起卡

```
Thread 0:  waiting for mutex
Thread 1:  ready
Thread 2:  ready
...
Thread 31: ready
```

**物理现实：**

```
Warp Scheduler:
┌─────────────────────────┐
│ Warp PC stalled         │
│ → 整个 Warp 不可前进    │
└─────────────────────────┘
```

📌 **问题名称：Forward Progress Failure**

---

### 3.2 Forward Progress 问题是什么？

 典型死锁场景（没有 ITS）

```cpp
__device__ int lock;

__global__ void kernel() {
    if (threadIdx.x == 0) {
        while (atomicCAS(&lock, 0, 1) != 0);
    }
    __syncthreads();
    // critical section
}
```

 发生了什么？

```
Thread 0: spinning (while loop)
Thread 1-31: already past lock
```

但：

```
Warp PC = 卡在 while
→ Thread 1-31 无法前进
→ __syncthreads 永远等不到
→ 死锁
```

⚠️ **不是程序逻辑错**
⚠️ 是 **Warp 锁步执行模型不支持“线程级前进”**

---

### 3.3 ITS 登场：Warp 内“解耦执行”

 🟢 Volta 及之后（Volta / Turing / Ampere / Hopper / Blackwell）
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/8790e76b8730442b91c0299bdff69bb9.png)
#### 3.3.1 Warp 结构发生了什么变化？

```
Warp
┌────────────────────────────────────┐
│ Thread 0: PC0, Active              │
│ Thread 1: PC1, Active              │
│ Thread 2: PC2, Active              │
│ ...                                │
│ Thread 31: PC31, Active            │
└────────────────────────────────────┘
```

👉 **PC 不再是 Warp 级唯一**
👉 **Active 状态是线程级**

---

#### 3.3.2 Warp Scheduler 现在在干嘛？

```
Warp Scheduler
        │
        ▼
┌──────────────────────────────┐
│ 从 Warp 中挑“可执行线程子集” │
│ 发射同一条指令                │
└──────────────────────────────┘
```

⚠️ 但注意这句话的关键限定：

> **仍然只能发射“同一条指令”**

---

### 3.4  ITS 如何解决 Forward Progress（配图）

 🔁 ITS 下的执行流程

```
Thread 0: PC = while(cond)
Thread 1: PC = __syncthreads
Thread 2: PC = __syncthreads
...
```

 Warp Scheduler 看到的是：

```
可执行线程：
- Thread 0 → 指令 A
- Thread 1-31 → 指令 B
```

执行顺序（简化）：

```
Cycle 1: 发射 B（Thread 1-31）
Cycle 2: 发射 A（Thread 0）
Cycle 3: 发射 B（Thread 1-31）
...
```

✔ Thread 1-31 **可以继续前进**
✔ __syncthreads 可以被正确抵达
✔ 不再因单线程阻塞全 Warp

👉 **Forward Progress 得到保证**

---

### 3.5 ITS 没有解决什么？
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/22882e7b48c3401aa7eb0db75a8d199f.png)
#### 3.5.1 ❌ ITS 没有解决 Divergence 的性能问题

这是**90%的人会误解的地方**。

---

  逻辑分支下，执行图并没有变

代码：

```cpp
if (cond) {
    A();
} else {
    B();
}
```

 物理执行仍然是：

```
Warp:
Group A threads
Group B threads
```

执行序列（仍然是串行）：

```
Active Mask = Group A
→ execute A

Active Mask = Group B
→ execute B
```

### 图示：

```
Time →
┌────────────┬────────────┐
│   A only   │   B only   │
└────────────┴────────────┘
```

❌ 没有并行
❌ 没有融合
❌ 吞吐仍然被分裂

---

#### 3.5.2 为什么 ITS 不可能解决 Divergence？

 根本原因只有一句话：

> **Warp Scheduler 一次只能发射“一条指令”**

```
Cycle N:
→ FADD R1,R2,R3   （不能同时发射 LDG）
```

即使：

* Thread 0 想执行 A
* Thread 1 想执行 B

❌ **硬件无法在同一 Warp 同时执行两条不同指令**

ITS 改的是 **“谁能前进”**
不是 **“一次能执行多少种指令”**

---

### 3.6 用一张对比图压缩理解

```
                 无 ITS                      有 ITS
────────────────────────────────────────────────────────
PC              Warp 级唯一                  线程级独立
阻塞            一人卡，全员停               局部停
Forward Progress ❌ 可能死锁                  ✅ 保证
Divergence 吞吐  ❌ 串行                      ❌ 仍然串行
SIMT 模型        锁步                        锁步 + 解耦
```


> **ITS 解决的是“活不活得下去”
> Divergence 影响的是“跑得快不快”**

## 4. 指令重播 (Instruction Replay)—— 为什么“只写了一条指令，硬件却执行了多次”

除了逻辑分支，还有一种情况会让 Warp 停滞，且更加隐蔽。这就是 **Instruction Replay**。

### 4.1 一句话先定性

> **Instruction Replay 不是软件循环**
> **而是同一条指令在硬件层面被“分批重发”**

⚠️ PC 没变
⚠️ 指令没变
⚠️ 只是 **Warp 没法一次性完成**

---

### 4.2 Shared Memory 的物理现实

#### 4.2.1 Shared Memory Bank 结构（以 32 bank 为例）

```
Shared Memory
┌────┬────┬────┬────┬────┬────┬────┬────┐
│B0  │B1  │B2  │B3  │B4  │B5  │B6  │B7  │ ...
└────┴────┴────┴────┴────┴────┴────┴────┘
  ↑     ↑     ↑
 Bank0 Bank1 Bank2 ...
```

* 每个 bank：**1 cycle 只能服务 1 个地址**
* Warp：**32 个线程同时访问**

---

### 4.3 理想情况（无 Bank Conflict）

#### 4.3.1 Warp 访问模式

```
Thread 0  → Bank 0
Thread 1  → Bank 1
Thread 2  → Bank 2
...
Thread 31 → Bank 31
```

#### 4.3.2 硬件执行图

```
Cycle N:
LD.SHARED executed once
┌────────────────────────────┐
│ 32 threads → 32 banks      │
│ All served in 1 cycle      │
└────────────────────────────┘
```

✔ 没有 Replay
✔ 吞吐满速

---

### 4.4 典型灾难：Shared Memory Bank Conflict

#### 4.4.1 冲突访问模式（4-way conflict 示例）

```
Thread 0  → Bank 0
Thread 1  → Bank 0
Thread 2  → Bank 0
Thread 3  → Bank 0
Thread 4  → Bank 1
Thread 5  → Bank 1
...
```

#### 4.4.2 Warp 视角（逻辑上）

```
Warp wants:
LD.SHARED [addr[t0..t31]]
```

#### 4.4.3 硬件现实（物理上）

```
Cycle N:
Serve Bank 0: Thread 0
Cycle N+1:
Serve Bank 0: Thread 1
Cycle N+2:
Serve Bank 0: Thread 2
Cycle N+3:
Serve Bank 0: Thread 3
```

---

### 4.5 Instruction Replay 的发生

#### 4.5.1 Replay 的真实样子

```
Warp PC = LD.SHARED

Replay #1:
Active Mask = threads served in this round

Replay #2:
Active Mask = next subset

Replay #3:
...

直到：
All threads complete
→ PC 前进
```

 图示（时间线）

```
Time →
┌────────┬────────┬────────┬────────┐
│ Replay │ Replay │ Replay │ Replay │
│ (t0)   │ (t1)   │ (t2)   │ (t3)   │
└────────┴────────┴────────┴────────┘
```

⚠️ **这是同一条指令**
⚠️ **不是循环**
⚠️ **Warp Scheduler 也没换指令**

---

### 4.6 为什么它叫 Instruction Replay，而不是 Stall？

这是一个非常关键的区分点。

| Stall         | Instruction Replay |
| ------------- | ------------------ |
| Warp 停着不动 | Warp 在“工作”      |
| PC 不前进     | PC 也不前进        |
| 吞吐为 0      | 吞吐 < 1           |
| 等待资源      | 分批完成           |

👉 **Replay = 被迫串行化的执行**

---

### 4.7 Instruction Replay ≠ Warp Divergence（千万别混）

```
Warp Divergence:
→ 不同指令，串行执行

Instruction Replay:
→ 同一条指令，多次执行
```

| 维度     | Divergence | Replay     |
| -------- | ---------- | ---------- |
| 指令     | 不同       | 相同       |
| 原因     | 控制流     | 结构冲突   |
| PC       | 多路径     | 单路径     |
| 优化手段 | 重构控制流 | 改访存布局 |

---

### 4.8 除了 Shared Memory Bank Conflict，还有哪些 Replay 触发源？

#### ✅ 4.8.1. Shared Memory Bank Conflict（最常见）

* 高阶 stencil
* 矩阵转置
* Reduction / Scan

---

#### ✅ 4.8.2. Global Memory Memory Coalescing 失败（部分场景）

⚠️ **注意：不是所有非合并访问都会 Replay**

典型触发：

```
Warp 内访问跨度 > 128B
→ 被拆成多个 memory transaction
→ 指令层面 replay
```

---

#### ✅ 4.8.3. Tensor Core / 特殊单元结构冲突（高级）

* HMMA / MMA 指令
* Warp 内子集参与（如 16 threads）
* 硬件需要分批完成

👉 表现形式也是 replay

---

#### ✅ 4.8.4. 部分原子操作（Atomics）

* 同一地址高冲突
* SM 内部串行化
* Warp 级 replay

---

#### 4.8.5❌ 不属于 Replay 的情况

* Cache miss → **stall**
* DRAM latency → **stall**
* Warp 数不足 → **pipeline bubble**

---

### 4.9 为什么 Replay 在 Nsight 里这么“阴险”？

因为：

* 源码：**只有一条指令**
* SASS：**只有一条指令**
* 但：

  ```
  inst_executed >> inst_issued
  ```

你会看到：

* `smsp__inst_executed_pipe_lsu.sum` 飙高
* IPC 看起来“没那么低”
* 但 kernel 时间明显变长

👉 **Replay 是“隐性吞吐杀手”**

---

### 4.10 一张“脑内最终模型图”

```
Warp issues instruction
        │
        ▼
是否结构冲突？
   │
 ┌─┴───────────┐
 │ 否           │→ 一次完成 → PC++
 │ 是           │
 │              ▼
 │         Instruction Replay
 │         (Active Mask slicing)
 │              │
 │         全部完成
 └──────────────┘
```


> **Instruction Replay 是硬件在替你“补救错误访问模式”
> 它能保证正确性，但不会保证性能**

## 5. 内存发散 (Memory Divergence) —— Warp 还在“锁步”，但内存已经四分五裂
到这里你已经把 **控制流（Divergence）→ 执行模型（ITS / Replay）→ 结构冲突** 都讲清了，**内存发散（Memory Divergence）正好是“访存侧的终极杀手”**，而且**最容易和 Replay / Coalescing 混在一起**。


### 5.1 一句话定性

> **Memory Divergence = Warp 内线程访问的内存“延迟不同步”
> 导致 Warp 被迫等待最慢的访存子集**

⚠️ 它不是控制流问题
⚠️ 也不是 Bank Conflict
⚠️ 更不是 Instruction Replay 本身

但它**经常和 Replay 同时出现**

---

### 5.2 从理想状态开始

#### 5.2.1 理想的 Memory 行为（完全 Coalesced + Cache Hit）

```
Warp threads: T0 T1 T2 ... T31
Access: A, A+4, A+8, ..., A+124
```

#### 物理行为

```
1 × 128B Memory Transaction
→ L1 Hit
→ Latency = ~20 cycles
```

#### 时间线

```
Cycle N:
LD.GLOBAL issued
Cycle N+20:
All threads data ready
→ Warp PC 前进
```

✔ 没有 Divergence
✔ Warp 执行流畅

---

### 5.3 Memory Divergence 是怎么产生的？

#### 5.3.1 Warp 内访问“逻辑相同”，但**物理落点不同**

例子：

```
Thread 0  → L1 hit
Thread 1  → L1 hit
Thread 2  → L2 hit
Thread 3  → DRAM miss
...
```

⚠️ 指令一样
⚠️ 地址合法
⚠️ 但 **访问路径不同**

---

### 5.4 内存发散的真实执行图

#### 5.4.1 Warp 视角

```
Warp issues:
LD.GLOBAL [addr[t0..t31]]
```

#### 5.4.2 硬件视角

```
Memory Subsystem:
┌─────────────────────────────┐
│ Sub-transaction A: L1 hit   │
│ Sub-transaction B: L2 hit   │
│ Sub-transaction C: DRAM     │
└─────────────────────────────┘
```

#### 5.4.3 时间线（关键）

```
Time →
┌────────────┬────────────┬──────────────┐
│   L1 hit   │   L2 hit   │   DRAM miss  │
└────────────┴────────────┴──────────────┘
             ↑
      Warp 在这里已经“没事可干”
```

👉 Warp 必须 **等最慢那一批线程**

---

### 5.5 Memory Divergence 和 Instruction Replay 的关系
#### ❗ 极易混淆点

> “是不是 Memory Divergence = Replay？”

❌ **不是**

#### 对比一张表
| 维度     | Memory Divergence   | Instruction Replay |
| -------- | ------------------- | ------------------ |
| 根因     | 不同访问路径 / 延迟 | 结构冲突           |
| 指令     | 1 次发射            | 多次发射           |
| PC       | 停住等待            | 停在原地重放       |
| 典型来源 | Cache miss / DRAM   | Bank conflict      |
| 是否串行 | 等最慢              | 被迫串行           |

👉 **Memory Divergence = 等**
👉 **Replay = 重做**

---

### 5.6 Memory Divergence 的典型触发场景

#### ✅ 1. Warp 内访问跨越多个 Cache Line

```
addr[t] = base + f(t)
f(t) 非线性 / 稀疏
```

结果：

* 多个 memory transaction
* 不同 cache line 命中情况不同
* 延迟被拉长

---

#### ✅ 2. Warp 内访问不同页面（TLB 层）

* 一部分 TLB hit
* 一部分 TLB miss → page walk

⚠️ TLB miss 延迟巨大
⚠️ Warp 级等待

---

#### ✅ 3. 访问冷热数据混合

```
部分线程 → 热数据（cache）
部分线程 → 冷数据（DRAM）
```

👉 逻辑一致
👉 性能灾难

---

#### ✅ 4. Pointer chasing / Graph / Hash

```
next = ptr[next]
```

Warp 内完全随机

👉 **Memory Divergence 是常态**

---

### 5.7 Memory Divergence ≠ Memory Coalescing 失败

### 常见误解

> “只要 coalesced 就不会 Memory Divergence？”

❌ 错

```
128B transaction 完美合并
但：
- 部分 cache hit
- 部分 miss
```

👉 **合并 ≠ 同步返回**

---

### 5.8 Warp Scheduler 在 Memory Divergence 下能做什么？

#### 5.8.1 只能：切 Warp

```
Warp A: waiting memory
Warp B: ready
→ Scheduler 切到 Warp B
```

#### 5.8.2 不能：

* ❌ 拆 Warp
* ❌ 提前提交 PC
* ❌ 加速慢线程

👉 Memory Divergence **完全靠 Warp 数掩盖**

---

### 5.9 一张“脑内执行模型图”

```
Warp issues LD
      │
      ▼
Memory Subsystems
┌───────────┬───────────┬────────────┐
│ L1 hit    │ L2 hit    │ DRAM miss  │
└───────────┴───────────┴────────────┘
                  │
                  ▼
          Warp waits slowest
```


> **Memory Divergence 是“访存层面的尾巴效应”
> Warp 的执行时间 = 最慢那几个线程**

## 6.完整 Warp 执行时间线总图
>这是一张 “从 Warp 被选中 → 执行 → 被拖慢 → 结束” 的真实时间线

```
Time ─────────────────────────────────────────────────────────▶

Warp selected by Scheduler
│
│  (1) 正常 SIMT 执行（Full Mask）
│  ┌─────────────────────────────┐
│  │ PC = I0                     │
│  │ Active Mask = 111...111     │
│  │ All threads execute         │
│  └─────────────────────────────┘
│
│  (2) Branch Divergence 出现
│  ┌──────────────┬──────────────┐
│  │ Path A       │ Path B       │
│  │ Mask = A     │ Mask = B     │
│  │ (serialize)  │ (serialize) │
│  └──────────────┴──────────────┘
│        ▲              ▲
│        │              │
│        └──── 同一 Warp，PC 不前进
│
│  (3) ITS 介入（Forward Progress）
│  ┌─────────────────────────────┐
│  │ 部分线程 stall               │
│  │ 其余线程可继续推进 PC        │
│  │ （仍然一次一条指令）          │
│  └─────────────────────────────┘
│
│  (4) 发射内存指令（LD / ST）
│  ┌─────────────────────────────┐
│  │ Warp issues LD               │
│  │ addr[t0..t31]                │
│  └─────────────────────────────┘
│
│  (5) Shared Memory Bank Conflict
│  ┌─────────┬─────────┬─────────┐
│  │ Replay1 │ Replay2 │ Replay3 │  ← Instruction Replay
│  │ Mask X  │ Mask Y  │ Mask Z  │
│  └─────────┴─────────┴─────────┘
│        ▲
│        └── 同一条指令，多次执行
│
│  (6) Memory Divergence（更阴险）
│  ┌─────────────────────────────┐
│  │ 部分线程 L1 hit              │
│  │ 部分线程 L2 hit              │

│  └─────────────────────────────┘
│            ▲
│            └── Warp 等最慢线程
│
│  (7) Warp 被换出（Latency Hiding）
│  ┌─────────────────────────────┐
│  │ Scheduler 切换到其他 Warp    │
│  └─────────────────────────────┘
│
│  (8) 最终完成（Tail Latency）

Warp retires

```

## 7. 优化策略：如何写出 Branchless 代码？

在系统性能工程中，我们要极力避免分支。以下是几种工业级的处理模式：

### 7.1 谓词化 (Predication) 与 Select 指令
编译器通常足够聪明，但手写 Branchless 代码能提供更强的保证。
*   **逻辑替换**：
    *   *Bad*: `if (val < 0) x = 0; else x = val;`
    *   *Good*: `x = max(0, val);` (直接映射到 PTX `max` 指令)
*   **Select 指令**：
    *   使用三元运算符 `z = (cond) ? a : b;`。
    *   在 PTX 层级，这会被编译为 `selp` (Select based on predicate)，完全没有控制流跳转，流水线满载。

### 7.2 数据重排 (Sort & Compact)
对于光线追踪或稀疏矩阵计算，Divergence 往往源于数据本身的无序性。
*   **策略**：在计算密集型 Kernel 执行前，先运行一个轻量级的 **Stream Compaction** 或 **Sort** Kernel。
*   **目的**：将走“分支 A”的数据聚拢到前 N 个 Warp，将走“分支 B”的数据聚拢到后 M 个 Warp。
*   **收益**：虽然多了一个 Kernel，但主 Kernel 的 Warp Divergence 降为 0，整体端到端性能通常会有显著提升。
