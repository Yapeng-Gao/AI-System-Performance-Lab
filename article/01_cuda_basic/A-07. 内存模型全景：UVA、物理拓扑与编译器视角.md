在 CPU 编程中，我们通常只需要关心 Stack 和 Heap。编译器、缓存层级以及 NUMA 拓扑大多被操作系统隐藏在抽象之下。

但在 GPU 的世界里，这种“抽象的善意”并不存在。

GPU 的内存层次结构不仅被拉伸得极长，而且不同层级之间的延迟与带宽差异跨越了多个数量级。更关键的是，这些差异并不会通过异常、告警或明显的 API 行为体现出来，而是直接体现在性能上。

许多 CUDA 程序“逻辑正确但性能异常”，并不是算法问题，而是程序在不知不觉中，把数据放到了一个你本不打算让它去的地方。

本章的目标，是建立 GPU 内存的空间感与控制感：
哪些内存层级仍然由你主导，哪些已经完全交给了编译器与硬件。

>这一次内存访问，
>是我控制的，
>还是编译器 / 硬件替我做的决定？

| 层级     | 你能不能控制 | 控制手段    | 失控代价      |
| -------- | ------------ | ----------- | ------------- |
| Register | ❌（部分）    | 减少压力    | Spill → Local |
| Local    | ❌            | 无          | HBM 延迟      |
| Shared   | ✅            | 布局 / bank | Replay        |
| L1       | ❌            | hint only   | cache miss    |
| L2       | ❌            | 几乎不可    | latency       |
| UVA      | ❌            | 只管地址    | 带宽灾难      |

## 1. GPU 内存不是一条“层级”，而是一张“拓扑”
在描述 GPU 内存时，我们常用“层级结构”这个词，但这容易让人产生一个错觉：
仿佛这些内存只是逻辑上分层，实际访问成本差别不大。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/6f83c866071941c585d6265ffa1539c4.png)
事实恰恰相反。

GPU 的每一次访存，实际上都沿着一条明确的物理路径传播：

```cpp
ALU
 ↓
Register File
 ↓
SM SRAM（Shared / L1）
 ↓
L2 Cache（跨 SM）
 ↓
Memory Controller
 ↓
HBM

```
这条路径越长，延迟越高；
路径上经过的共享节点越多，争用与不确定性就越强。

性能问题的第一性原理不是“你访问了哪种内存”，
而是“你的访问走了多远”。

## 2. Register：你唯一能真正“假设很快”的地方

寄存器是 GPU 中唯一可以被合理地视为“常数时间访问”的存储。

* 位于 SM 内部
* 每线程私有
* 无一致性、无争用
* 直接供 ALU 消费

GPU 能在一个 SM 上同时驻留大量线程，并不是因为切换开销低，而是因为**每个线程的上下文早已完整地存在寄存器文件中。**为了支撑成千上万个线程的上下文切换（Context Switch），GPU 的 RF 极其巨大（H100 每个 SM 有 64K 个 32-bit 寄存器）。这是 GPU 能同时挂起上万个线程、靠 Warp 切换掩盖延迟的根本。

但这也意味着一个残酷的事实：
>寄存器既是性能的上限，也是性能崩塌的起点。

### 2.1 寄存器不是“慢慢不够用”，而是“瞬间溢出”

当寄存器压力超过阈值时，编译器不会给你任何提示，而是直接采取最保守的方案：

* 将部分变量溢出到 Local Memory
* 维持语义正确
* 接受性能坠崖

这种转变不是渐进的，而是**离散的**。
Kernel 可能只多加了一个中间变量，性能却下降数倍。



## 3.Shared Memory 与 L1：同源 SRAM，不同哲学
  Shared Memory 与 L1 Cache 在物理上通常共享 SM 内的一块 SRAM，但它们代表了两种完全不同的设计哲学：

   *   **L1 Cache**
   		* 	硬件管理，对程序员透明。在 Hopper 之前，它与 Texture Cache 往往是一体的。不仅缓存 Global Memory 的读取，还负责处理 Register Spilling。也是寄存器溢出的第一缓冲区
   		* 面向“不确定的访问模式”
   		* 本质是容错机制
   *   **Shared Memory**：
	   * 软件管理（Programmer-Managed Cache）。这是 CUDA 编程的灵魂。它是线程块（Block）内通信的高速公路，也是 **TMA (Tensor Memory Accelerator)** 搬运数据的目的地。
	   * 面向“可预测的协作模式”
	   * 是性能设计工具

这是 GPU 内存体系中，最后一层“你还能亲自布置”的空间。
Shared Memory 的价值不在于“快”，而在于：
>它是你能明确知道“数据此刻在哪”的极少数地方之一。

这也是为什么所有高性能算子（GEMM、Attention、Stencil）最终都会回到 Shared Memory。


## 4. L2 Cache：一致性的边界
L2 是 GPU 中第一个跨 SM 共享的存储层级,所有 SM 共享，通过 **Crossbar** (纵横开关) 连接。它承担的角色远不止“缓存”：

* 它是 **PoC (Point of Coherence)**，即数据一致性的边界
* P2P / NVLink 的中转节点
* 原子操作的聚合点
* Unified Memory 迁移的重要观察者

在许多 Nsight 报告中，L2 Miss 被简单理解为“带宽问题”，但实际上：L2 的行为，**往往反映的是整个程序的数据布局与访问节奏是否合理**。

从 Ampere (40MB) 到 Blackwell，L2 容量激增。这是为了缓解 HBM 带宽增长滞后于算力增长的矛盾，旨在捕获更多的时间局部性（Temporal Locality）。但 L2 的延迟已经是寄存器的两个数量级。
## 5.  Global Memory (Device Memory)：不是慢，是太远
这是我们通常所说的“显存”：
    *   **物理位置**：GPU 芯片周围的 **HBM** 或 **GDDR** 显存颗粒。
    *   **特性**：容量大（80GB+），但延迟极高（几百个时钟周期）。它是唯二能持久化数据的地方（另一个是 Host Memory）。

一旦访问路径落到这里，性能优化空间就已经非常有限。

## 7. 命名陷阱：逻辑空间 vs 物理存储

CUDA 编程模型中定义的内存空间（Memory Spaces），并不一定直接对应物理硬件。这是新手最容易翻车的地方。
![在这插入图片描述](https://i-blog.csdnimg.cn/direct/55518810ba3a4f7ba01a729f80bf1a41.png)
逻辑视图
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/ff276e3205524412a2358aabd0579519.png)
物理视图
### 7.1 Local Memory：最危险的误称
*   **逻辑定义**：线程私有（Thread Private）。看起来像是寄存器的扩展。
*   **物理真相**：**它存储在 Global Memory (HBM) 中！**
*   **性能影响**：
	1. 	延迟高：访问 Local Memory 本质上是在访问显存。
	2. 缓存污染 (Cache Pollution)：Local Memory 的读写会经过 L1/L2 Cache。大量的 Register Spilling 会挤占 L1 Cache 中的有用数据（如 Global Memory 的热数据），导致整体 Cache Hit Rate 下降。
*   **触发条件 (Register Spilling)**：
    1.  Kernel 使用的寄存器超过了硬件限制（或 Launch Bounds 限制）。
    2.  在 Kernel 内部定义了无法静态索引的大数组（编译器无法将其放入寄存器）。
*   **诊断**：在 SASS 汇编中看到 `LDL` (Load Local) 或 `STL` (Store Local) 指令时，通常意味着性能报警。
>Local Memory 是 CUDA 中唯一一种：
>你没有显式使用，却能决定 Kernel 80% 性能的内存
### 7.2 Constant Memory：不是“小而快”，而是“统一才快”
*   **逻辑定义**：只读，64KB 限制。
*   **物理真相**：数据存储在 Global Memory 中，但在每个 SM 上有专用的 **Constant Cache**。
*   **广播机制**：当 Warp 内所有 32 个线程读取同一个地址时（Uniform Access），数据会从 Cache 中**广播**给所有线程，只需一个周期。但如果线程读取不同地址，访问被序列化,性能会线性下降。
>Constant Memory 的本质是 Warp-Uniform Cache

## 8. UVA (Unified Virtual Addressing)：统一的是地址

为什么我们可以把 CPU 的指针直接传给 Kernel？为什么 `cudaMemcpy` 知道指针是在 Host 还是 Device？

### 8.1 虚拟地址空间的统一
在 64 位系统下，CUDA 驱动程序启用 **UVA** 机制：
*   **单一地址空间**：CPU 内存、GPU 显存、甚至通过 NVLink 连接的其他 GPU 显存，都被映射到同一个 64 位虚拟地址空间中。
* P2P (Peer-to-Peer)：这是多卡通信的基石。GPU0 的 Kernel 可以直接解引用一个指向 GPU1 显存的指针（只要该地址在 UVA 范围内），硬件会自动走 NVLink 通道。
*   **地址分段**：驱动程序通过指针的高位地址范围，就能判断这个指针指向哪里（Host? Device 0? Device 1?）。
*   **意义**：简化了编程模型，使得指针可以在不同设备间传递而保持语义不变。

### 8.2 Zero-Copy (零拷贝)
Zero-Copy 的吸引力在于“省去 memcpy”，但它绕不开 PCIe 的物理限制。
基于 UVA，我们可以实现 **Zero-Copy**：
*   **机制**：使用 `cudaHostAlloc` (Pinned Memory) 分配的 Host 内存，GPU Kernel 可以直接通过 PCIe 总线读取，而不需要显式的 `cudaMemcpy`。
*   **场景**：
    *   **优势**：对于只读一次的小数据，省去了 Launch DMA Engine 的开销。
    *   **劣势**：PCIe 带宽（~64GB/s）远低于 HBM 带宽（~3000GB/s）。高频访问会导致严重瓶颈。

### tips:
>UVA 解决的是：能不能解引用
>不是：该不该解引用

工程禁令：
* ❌ 在 Kernel 中循环访问 Host 指针
* ❌ 把 Zero-Copy 当 Global Memory
* ❌ 把 P2P 当本地 HBM

地址统一，并不意味着物理距离消失。

## 9. 编译器优化：`__restrict__` 的契约精神

在 C++ 高性能编程中，指针别名（Pointer Aliasing）是阻止编译器优化的最大障碍。在 GPU 上，这个问题被放大了。

### 9.1 别名是优化的天敌
考虑函数 `void add(float* a, float* b, float* c)`。编译器必须假设 `c` 可能指向 `a` 或 `b` 的中间。
*   **后果**：编译器不敢进行激进的指令重排，也不敢将多次读取合并。更重要的是，它可能不敢生成向量化加载指令（`LDG.128`），因为怕读写顺序改变导致数据竞争。

### 9.2 `__restrict__` 的承诺

```cpp
void add(float* __restrict__ a,
         float* __restrict__ b,
         float* __restrict__ c);
```
你在说：
>这些指针，绝不别名。

编译器因此敢于：
    1.  **启用 Read-Only Cache**：译器可能会生成 LDG.NC (Non-Coherent) 指令。这允许数据走 Texture Cache 路径，绕过部分 L1 一致性协议，从而获得更高的有效带宽。
    2.  **向量化加载**：更容易生成 128-bit (float4) 的 Load/Store，大幅减少指令数。
    3.  **寄存器缓存**：编译器敢于将数据缓存在寄存器中，而不是每次都去读内存。
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/57b1584a246b438aa91be23d68f5a9f0.png)
⚠️ 这是契约，不是 hint。
一旦违约，结果不是“慢”，而是悄悄算错

## 10. L1 与 Shared：谁占地盘，谁决定命运

SM 内部的 SRAM（例如 128KB）是有限的，L1 Cache 和 Shared Memory 就像两个抢地盘的租客。

### 10.1 硬件分区模式
*   **可配置性**：CUDA 允许开发者通过 `cudaFuncSetAttribute` 调整分界线。
    *   `cudaFuncAttributePreferredSharedMemoryCarveout`
*   **权衡**：
    *   **Shared 优先**：适用于严重依赖 Shared Memory 进行 Tiling 的算子（如 GEMM, Conv）。更大的 Shared Memory 意味着更高的 Occupancy。
    *   **L1 优先**：适用于 Element-wise 或不规则访存算子。更大的 L1 能吸收更多的 Global Memory 突发流量和溢出的寄存器数据。

*注意：从 Hopper 架构开始，L1 和 Shared Memory 的硬件实现更加解耦，虽然 API 依然兼容，但物理上的竞争关系有所改变，以适应异步 TMA 的需求。*

## 11. 从语义到物理的对照表
```
┌────────────┬──────────────┬────────────┬──────────────┐
│ CUDA 语义  │ 逻辑归属      │ 物理位置    │ SASS 证据     │
├────────────┼──────────────┼────────────┼──────────────┤
│ Register   │ Thread        │ RF          │ R0–R255      │
│ Local      │ Thread        │ HBM          │ LDL / STL    │
│ Shared     │ Block         │ SM SRAM     │ LDS / STS    │
│ Global     │ Grid          │ HBM          │ LDG / STG    │
│ Constant   │ Grid (RO)     │ HBM + Cache │ LDC          │
│ Param      │ Kernel        │ Param Mem   │ LD.PARAM     │
└────────────┴──────────────┴────────────┴──────────────┘

```
